# `deployable.target_unsupported`

A deployable reaches something its target can't run.

## Why Jadpo refuses it

A deployable is held to what it reaches, from the routes of the APIs it
serves and the background work it runs. Some of that can't work on its
target: a Worker has no disk, runs no service beside the app and can't send
mail on port 25, and only a Worker receives a Cloudflare queue or counts in
Cloudflare's rate-limiting binding. Catching it here means the app doesn't
fail in production, the first time a request gets that far.

Jadpo won't pick the replacement for you, since it decides where your data
or your work lives. Each refusal names what to use instead.

## What it looks like

A bakery keeps its suppliers' price sheets on its disk:

```jadpo check project=e-deployable-target-unsupported file=app.jadpo hidden
application {
    connections: {
        sheets: {
            driver: Driver.disk
            path: "/var/lib/bakery/sheets"
        }
    }
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/types/sheet_text.jadpo hidden
/// A price sheet as a supplier sends it.
type SheetText = Text {
    min_length: 1
    max_length: 100000
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/types/new_sheet.jadpo hidden
use bakery/types { SheetText }

/// A price sheet to keep.
type NewSheet = Input {
    text: SheetText
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/types/sheet_kept.jadpo hidden
use bakery/entities { PriceSheet }

/// The sheet as kept.
type SheetKept = Output {
    id: PriceSheet.id
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/failures/sheet_not_kept.jadpo hidden
/// The sheets store had no room for a sheet.
type SheetNotKept = Failure {
    kind: FailureKind.unavailable
    message: "There was no room to keep the sheet."
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/entities/price_sheet.jadpo hidden
/// A supplier's price sheet, kept as it was sent.
entity PriceSheet {
    id: Uuid
    sheet: File {
        store: sheets
        max_size: 5mb
        types: [FileType.csv]
    }

    policy: {
        create: [Access.public]
        read: [Access.public, Access.system]
    }
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/actions/keep_prices.jadpo
use app { sheets }
use bakery/entities { PriceSheet }
use bakery/types { NewSheet, SheetKept }
use bakery/failures { SheetNotKept }

/// Keeps a price sheet as it was sent.
action keep_prices(input: NewSheet) fails SheetNotKept -> SheetKept {
    var sheet: File = attempt sheets.put(encoding.to_utf8(input.text), FileType.csv) {
        storage_full: SheetNotKept
    }
    var filed: PriceSheet = PriceSheet.create {
        set: {
            sheet: sheet
        }
    }
    return SheetKept {
        id: filed.id
    }
}
```

```jadpo check project=e-deployable-target-unsupported file=domains/bakery/routes/tariffs.jadpo hidden migrate=initial
use bakery/types { NewSheet, SheetKept }
use bakery/actions { keep_prices }

/// The suppliers' tariffs.
routes Tariffs {
    prefix: /tariffs

    /// Keeps a price sheet.
    POST / {
        authentication: RouteAuthentication.none
        input: NewSheet
        output: SheetKept
        status: SuccessStatus.created
        run: keep_prices(input)
    }
}
```

```jadpo check project=e-deployable-target-unsupported file=api/main.jadpo_record hidden
// Generated by Jadpo from the routes of API main; update it with `jadpo api update`, never by hand.
record api 1

GET /openapi.json
    generated openapi
    authentication none
    status 200

POST /tariffs
    authentication none
    input NewSheet (body)
    output SheetKept
    status 201
    fails sheet_not_kept

input NewSheet
    text: Text { min_length: 1, max_length: 100000 }

output SheetKept
    id: Uuid

failure sheet_not_kept
    status 503
    message "There was no room to keep the sheet."
```

Its edge, which serves the API that keeps them, is built for Workers:

```jadpo check project=e-deployable-target-unsupported expect=deployable.target_unsupported file=app.jadpo
application {
    connections: {
        limits: {
            driver: Driver.cloudflare_rate_limits
            namespace: 1001
        }
        sheets: {
            driver: Driver.disk
            path: "/var/lib/bakery/sheets"
        }
    }
    deployables: {
        edge: {
            serves: [main]
            target: Target.wasm
        }
    }
    rate_limits: {
        store: limits
    }
}
```

```text output
error: `edge` can't use `sheets` on Workers, which has no disk
 --> app.jadpo:15:21
   |
 7 |         sheets: {
   |         ------ `Driver.disk`
15 |             target: Target.wasm
   |                     ^^^^^^^^^^^ built for Workers
  reason: `sheets` keeps files on the server's own disk (`Driver.disk`), and a Worker has none; `edge` uses it through `keep_prices`.
  next: Keep `sheets`'s files through a package over S3's API, such as Cloudflare R2, or use them from a `Target.native` deployable (agent)
  rule: deployable.target_unsupported
  help: https://jadpo.dev/docs/errors/deployable.target_unsupported

check failed: 1 error, 8 files
```

`(agent)` at the end of the `next:` line means your coding agent can make
the fix itself.

A deployable built for Workers that runs the schedules is held to them too.
A Worker ticks on Cloudflare's cron, once a minute at most, so a schedule
due more often is refused at its `every:`. Here a bakery checks its ovens
twice a minute:

```jadpo check project=e-deployable-schedule-workers file=app.jadpo hidden
application {
    connections: {
        main: {
            driver: Driver.postgres
        }
    }
}
```

```jadpo check project=e-deployable-schedule-workers file=domains/bakery/actions/check_ovens.jadpo hidden
/// Checks the ovens' temperatures, which changes nothing here.
action check_ovens() -> Unit {
    assert 1 == 1
}
```

```jadpo check project=e-deployable-schedule-workers file=domains/bakery/schedules/oven_check.jadpo migrate=initial
use bakery/actions { check_ovens }

/// Checks the ovens twice a minute.
schedule oven_check {
    every: 30s
    run: check_ovens()
}
```

and runs its schedules on Workers:

```jadpo check project=e-deployable-schedule-workers expect=deployable.target_unsupported file=app.jadpo
application {
    connections: {
        main: {
            driver: Driver.postgres
        }
    }
    deployables: {
        edge: {
            runs: [Trigger.schedules, Trigger.subscribers]
            target: Target.wasm
        }
    }
}
```

```text output
error: `edge` can't run `oven_check` every 30 seconds on Workers, whose cron runs once a minute
 --> domains/bakery/schedules/oven_check.jadpo:5:12
  |
5 |     every: 30s
  |            ^^^ more often than once a minute
  reason: A Worker ticks when Cloudflare's cron trigger runs it, once a minute at most, so a schedule due every 30 seconds would run late; `edge` runs `oven_check` because its `runs:` lists `Trigger.schedules`.
  next: Give `oven_check` `every: 1m` or longer, or run `Trigger.schedules` in a `Target.native` deployable (agent)
  rule: deployable.target_unsupported
  help: https://jadpo.dev/docs/errors/deployable.target_unsupported

check failed: 1 error, 3 files
```

Its `client_address:` is held to the target as well: Cloudflare's
`CF-Connecting-IP` is the only source a Worker reads. Here a bakery reads
its customers' addresses from its load balancer's `X-Forwarded-For`, and
serves them from Workers:

```jadpo check project=e-deployable-client-address-workers expect=deployable.target_unsupported file=app.jadpo
application {
    client_address: {
        source: ClientAddressSource.forwarded_for
        hops: 1
    }
    connections: {
        limits: {
            driver: Driver.cloudflare_rate_limits
            namespace: 1001
        }
    }
    deployables: {
        edge: {
            serves: [main]
            target: Target.wasm
        }
    }
    rate_limits: {
        store: limits
    }
}
```

```text output
error: `edge` can't read the client's address from `X-Forwarded-For` on Workers
 --> app.jadpo:3:17
   |
 3 |         source: ClientAddressSource.forwarded_for
   |                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ not read on Workers
15 |             target: Target.wasm
   |                     ----------- built for Workers
  reason: Cloudflare writes the client's address in `CF-Connecting-IP` on every request, overwriting a caller's, and a Worker has no connection address of its own, so `cloudflare` is the only source a Worker reads; `edge` would refuse to start.
  next: Use `ClientAddressSource.cloudflare` without `hops:`, or build `edge` with `Target.native` (agent)
  rule: deployable.target_unsupported
  help: https://jadpo.dev/docs/errors/deployable.target_unsupported

check failed: 1 error, 1 file
```

## How to fix it

The question is whether the work has to stay on that target.

**If it doesn't have to run on Workers**, build it natively, where a disk
is available:

```jadpo fragment
        edge: {
            serves: [main]
            target: Target.native
        }
```

```jadpo check project=e-deployable-target-unsupported-native file=app.jadpo hidden
application {
    connections: {
        sheets: {
            driver: Driver.disk
            path: "/var/lib/bakery/sheets"
        }
    }
    deployables: {
        edge: {
            serves: [main]
            target: Target.native
        }
    }
}
```

```jadpo check project=e-deployable-target-unsupported-native file=domains/bakery/types/sheet_text.jadpo hidden
/// A price sheet as a supplier sends it.
type SheetText = Text {
    min_length: 1
    max_length: 100000
}
```


`edge` now keeps its sheets on the server's disk. To stay on Workers, keep
the files through a package over S3's API, such as Cloudflare R2.

**If a schedule runs too often for Workers**, give it `every: 1m` or longer:

```jadpo fragment
schedule oven_check {
    every: 1m
    run: check_ovens()
}
```

```jadpo check project=e-deployable-schedule-workers-fix file=domains/bakery/schedules/oven_check.jadpo hidden
use bakery/actions { check_ovens }

/// Checks the ovens once a minute.
schedule oven_check {
    every: 1m
    run: check_ovens()
}
```

```jadpo check project=e-deployable-schedule-workers-fix file=app.jadpo hidden
application {
    connections: {
        main: {
            driver: Driver.postgres
        }
    }
    deployables: {
        edge: {
            runs: [Trigger.schedules, Trigger.subscribers]
            target: Target.wasm
        }
    }
}
```

```jadpo check project=e-deployable-schedule-workers-fix file=domains/bakery/actions/check_ovens.jadpo hidden migrate=initial
/// Checks the ovens' temperatures, which changes nothing here.
action check_ovens() -> Unit {
    assert 1 == 1
}
```

The ovens are now checked each time the Worker's cron runs, once a minute.

**If it reads the client's address from a header on Workers**, use
`cloudflare`, with no `hops:`:

```jadpo check project=e-deployable-client-address-workers-fix file=app.jadpo
application {
    client_address: {
        source: ClientAddressSource.cloudflare
    }
    connections: {
        limits: {
            driver: Driver.cloudflare_rate_limits
            namespace: 1001
        }
    }
    deployables: {
        edge: {
            serves: [main]
            target: Target.wasm
        }
    }
    rate_limits: {
        store: limits
    }
}
```

Rate limits now count the address Cloudflare gives each request.
