# The `.jadpo_record` format

How every committed file Jadpo generates is written, so that it reads well
in a pull request, merges cleanly, is fast and exact for the compiler, and
is coloured and folded in editors. Richard decided on 2026-10-16 that these
files share the extension `.jadpo_record`, sit next to what they describe,
use Jadpo's readable form rather than JSON, start with a line saying what
generated them and which command updates them, and are regenerated by
`jadpo check`, a hand edit being an error. This page designs the format
itself. It is a proposal: nothing here is decided until Richard says so.

## Recommendation

Use **one small line-oriented format, an outline of Jadpo's own words**,
for every record, with `jadpo.lock` written in it too:

- **Two levels and no braces.** An entry's heading starts in column 0 (`POST
  /todos`, `type Booking = Object`, `operation bookings.create`); its facts
  follow, one per line, indented four spaces. A blank line separates
  entries. There are no closing braces, so a change touches only the lines
  of the fact that changed, and git's default hunk header names the entry.
- **Values are Jadpo.** Names, strings, numbers and type expressions are
  written exactly as the formatter writes them in source, on one line
  (`Text { min_length: 1, max_length: 200 }`), and descriptions are `///`
  lines. A reviewer reads one language, and the editor grammar reuses the
  `.jadpo` grammar's rules for values.
- **Two kinds of line in an entry.** A field is `name: value`, as in source.
  Every other fact starts with a lower-case keyword from a closed list per
  record kind (`status 201`, `fails todo_not_found`, `file types/booking.jadpo`).
  Lists repeat the keyword, one item per line.
- **Two shapes of record.** *Views* (the API record, package surfaces) are
  recomputed from today's source; they use the outline. *Ledgers* (the
  identity registry, translation sources, the lock) hold history the source
  no longer has; each entry is one self-contained line, go.sum style, so
  git's built-in `union` merge can combine two branches' additions.
- **Line 1 is the header comment, line 2 is `record <kind> <format>`.** No
  timestamps, compiler versions, counts or alignment anywhere, so nothing
  changes unless the promise changes.
- **Order is by identity.** Entries are sorted by what identifies them,
  using the born name where a thing has been renamed, so a rename changes
  lines in place instead of moving a block.
- **Editors:** a hand-written TextMate grammar, `source.jadpo-record`, in
  `editors/vscode`, plus `jadpo lsp` serving records (out-of-date errors,
  outline, file links, group folding). **GitHub** shows plain text until
  Jadpo is in Linguist, and the format is designed to read well without
  colour; `.gitattributes` keeps the diffs expanded, forces LF and sets the
  ledgers' merge.

The rest of this page gives the needs, the prior art, three candidates, the
format in full, an example of every record kind, editor and GitHub support,
how diffs read, and five open questions.

## What the format must do

| Need | What it asks of the format |
|---|---|
| Review in a pull request | One fact per line; stable order; nothing that changes on its own (timestamps, counters, totals, alignment); a change to one route touches only its lines; the entry is visible beside every changed line |
| Renames | Show as a changed line, not a removed block and an added one |
| Merges | Two branches changing different things merge cleanly; the rest conflict small and obviously, with one command to resolve them |
| The compiler | Written in one pass from the graph; compared byte for byte; parsed in one pass without the Jadpo parser; a hand edit detected |
| Agents | Grep finds an entry by its heading; each entry points at its file; `--json` commands exist for structured reads |
| Versioning | A future Jadpo can change a kind's format, and an old Jadpo refuses a newer one rather than guessing |
| Size | Stripe's surface (estimate: about 500 operations and over a thousand types) stays one usable file |
| Editors and GitHub | Highlighting and folding from a simple grammar; readable as plain text where there is none |

## Prior art

| File | Shape | What to take | What to avoid |
|---|---|---|---|
| API Extractor `.api.md` (Microsoft) | Markdown wrapping the package's TypeScript declarations; header "Do not edit this file" | Committed, reviewed surface; diff is the review; the language's own syntax | Braces and nesting; declaration order rather than a canonical one |
| Android metalava `api/current.txt` | Java-like signatures, one member per line, sorted; first line `// Signature format: 4.0` | One member per line; format version on the first lines; sorted | |
| Swift `.swiftinterface` | Swift source; header comments `// swift-interface-format-version: 1.0` | Format version in a header comment | Compiler version in the header, which churns on every upgrade |
| Elm `docs.json` | JSON, generated; `elm diff` decides the version | The surface decides the version | JSON for something people read |
| Cargo.lock | TOML, `[[package]]` sorted by name; header "@generated … not intended for manual editing"; `version = 4` | Header, format number, sorted entries | Multi-line entries that conflict together |
| Go `go.sum` | One line per module and hash, sorted | One self-contained line per entry; trivially merged and grepped | Unlabelled positional fields |
| Terraform `.terraform.lock.hcl` and plan output | The lock in the tool's own HCL; the plan as an indented outline with `+ - ~` | A record in the tool's own syntax is possible; the plan reads well as an outline | |
| Prisma schema | Its own DSL, formatted by `prisma format` | A canonical formatter owns layout | |
| OpenAPI (YAML) | Deeply nested mappings | | Depth: a field sits five levels down; `$ref`s make a route unreadable alone |
| Protobuf descriptors | Binary `FileDescriptorSet`, compared by `buf breaking` | Compare by meaning when the git diff is not enough | Binary records |

The closest prior art, API Extractor and metalava, both reuse their
language's declarations and put one member on a line. Candidate A follows
the first; the recommendation follows the second.

## Three candidates

### A. Jadpo declarations

Records are unnamed declarations in ordinary Jadpo syntax, as `translations
{ }` and `acceptance { }` already are, parsed and formatted by the existing
crates:

```text
api_record main {
    routes: {
        "POST /todos": {
            authentication: RouteAuthentication.none
            input: CreateTodo
            output: TodoView
            status: 201
        }
    }
    types: {
        TodoView: Output {
            id: Uuid
            title: Text { min_length: 1, max_length: 200 }
        }
    }
}
```

- **For:** no new grammar, parser, formatter or highlighting; the API
  Extractor and `.swiftinterface` precedent.
- **Against:** four levels of nesting and a closing brace per level, so
  hunks are longer and conflicts land on ambiguous `}` lines. Only the outer
  declaration starts in column 0, so every hunk header on GitHub says
  `api_record main {`. Record-only content (resolved paths, statuses,
  digests, wire encodings, file pointers) would need syntax that source code
  never uses, growing the language for files nobody writes. The formatter
  keeps written order and records need sorted order. And a record that looks
  like source invites agents to edit it.

### B. An outline of Jadpo words (recommended)

Column-0 headings, four-space facts, Jadpo values, no braces except inside
a type expression on one line:

```text
POST /todos
    authentication none
    input CreateTodo (body)
    output TodoView
    status 201

output TodoView
    id: Uuid
    title: Text { min_length: 1, max_length: 200 }
```

- **For:** one fact per line; the entry's heading is in every hunk; depth
  never exceeds two indents; a one-pass parser that needs no Jadpo parser;
  close to what chunk 4.1 already writes for `api/main.api`.
- **Against:** a second, small grammar to keep (about forty lines of
  TextMate and a line splitter in Rust); grep on a fact line shows the fact
  without its heading (`rg -B` or `jadpo package show` give it).

### C. Flat facts

Every line carries its whole path, as go.sum does:

```text
route POST /todos authentication none
route POST /todos input CreateTodo body
route POST /todos output TodoView
route POST /todos status 201
type TodoView field id Uuid
type TodoView field title Text { min_length: 1, max_length: 200 }
```

- **For:** every line stands alone, so grep and `union` merges always work.
- **Against:** the heading repeats on every line, roughly tripling Stripe's
  surface (estimate), a route reads as six near-identical lines, and
  descriptions have nowhere natural to go.

**Off-the-shelf formats.** JSON is ruled out. YAML gives GitHub colour for
free, but its `#` comments, implicit typing and `{` flow mappings clash with
Jadpo's `//` and its constraint braces, and it needs a parser for a format
Jadpo controls fully. TOML suits a lock and little else.

| | A. Declarations | B. Outline | C. Flat facts |
|---|---|---|---|
| Diff of one changed fact | 1 line, entry often off-screen | 1 line, entry in the hunk | 1 line, self-describing |
| Hunk header | Always the outer declaration | The entry | The previous line |
| Merge of two additions | Conflicts near shared `}` | Clean unless adjacent | Clean with `union` |
| Size of a large surface | Medium | Smallest | Largest |
| New grammar to keep | None | Small | Smallest |
| Reads as | Source to edit | A generated outline | A ledger |

B wins for views, which people read; C wins for ledgers, which tools read
and branches append to. The recommendation is B, whose ledgers are written
as single-line entries, which are C's lines inside B's grammar.

## The format

### Views and ledgers

| Shape | Records | Source of truth | Entries | Merge |
|---|---|---|---|---|
| View | API record, package surface | Today's source | Outline: heading and facts | Normal; resolve by rerunning the command |
| Ledger | Identity registry, translation sources, lock | The record itself (history) | One line each | `merge=union`, then `jadpo check` validates |

### The header

Line 1 is a comment from one template; line 2 names the kind and its format:

```text
// Generated by Jadpo from <what it describes>; update it with `<command>`, never by hand.
record <kind> <format>
```

- `<kind>` is one of `api`, `identities`, `translations`, `surface`, `lock`.
  The path already implies it, but stating it lets a reader, `jadpo
  records` and the editor know the kind without path rules, and catches a
  file in the wrong place.
- `<format>` is a whole number per kind (below). There is no compiler
  version, date or digest in the header: each would change on every
  upgrade or every change, and a digest line would make every pair of
  branches conflict on line 2.
- Any other `//` line is a hand edit. `///` lines are content.

### Grammar

```text
file       = header-line record-line { blank-line entry }
header     = "// Generated by Jadpo from " text "; update it with `" command "`, never by hand." LF
record     = "record" SP kind SP integer LF
entry      = heading LF { member LF }
heading    = keyword { SP value }                         column 0
member     = INDENT ( doc | field | fact ) LF { INDENT INDENT field LF }
doc        = "///" [ SP text ]                            a description line
field      = name ":" SP value { SP qualifier }           as in source
fact       = keyword { SP value }                         keyword from the kind's closed list
value      = name | dotted-name | path | url | string | integer | version
           | digest | hash | type-expression | name ":" SP type-expression
           | "(" qualifier { SP word } ")"
```

- A line's kind is known from its first characters: column 0 is a heading;
  after the indent, `///` is a description, `name:` is a field, anything
  else is a fact. No line depends on the line before it, which is what makes
  the editor grammar and the parser simple and fast.
- The second indent exists only for fields that belong to a fact: an enum
  variant's fields in the API record, as chunk 4.1 already writes them.
  Nothing goes deeper.
- A ledger entry is a heading with no members.
- Values: names and dotted names as area 1 spells them; `path` is a URL path
  with `{name: Type}` placeholders or a file path relative to the record's
  folder; `string` is a Jadpo string; `type-expression` is Jadpo's, on one
  line; `digest` is `sha256:` and 64 lower-case hex digits; `hash` is 12
  lower-case hex digits (not a security check, so 48 bits is plenty).

### Layout and escaping

- UTF-8 without a byte-order mark, LF line endings, a final newline, no
  trailing spaces, no tabs. One space between tokens and never alignment, so
  a long new name cannot re-indent its neighbours.
- One blank line between entries that have members. Consecutive one-line
  entries (ledgers, and member-less headings) have none.
- Strings use Jadpo's escapes and only those: `\"`, `\\`, `\n`, `\r`, `\t`.
  Every other character is written as itself.
- A description is the declaration's first paragraph, joined onto one `///`
  line, so rewrapping the source comment changes nothing (open question 3).
  Its text follows `/// ` to the end of the line and needs no escaping;
  trailing spaces are dropped.
- Paths and URLs are never quoted: Jadpo file names are lower snake case,
  and URLs are written as the source gives them, which cannot contain a
  space.
- Booleans are facts that are present or absent (`changes`, `idempotent`,
  `accepted`), one per line, never `changes: true`.

### Ordering

Everything is sorted; nothing is in written order except a function's
parameters, which are part of its signature.

| Record | Sections, in order | Within a section |
|---|---|---|
| `api` | `api`, routes, named types, failures | Routes by path, then method in `GET POST PUT PATCH DELETE HEAD OPTIONS` order; types by born name; failures by code |
| `surface` | `package`, `provider`, `provides`, operations, actions, polls, events, functions, messages, types, failures, recipes | By born name; operations by `resource.operation` |
| `identities` | One section | By born name, then kind |
| `translations` | One section | By locale, then member |
| `lock` | One section | By package name and major version |

- **Facts inside an entry** come in a fixed order per entry kind (the
  examples below show it), and repeated facts (`fails`, `host`, `setting`)
  are sorted by value.
- **Fields are sorted by name**, not kept in written order: field order is
  not part of a JSON contract, so reordering fields in source changes no
  record. This changes chunk 4.1's record, which keeps written order.
- **Born name.** Where the identity registry has a line for a thing, it sits
  where its born name sorts. A renamed type therefore changes its heading
  and references in place, and the diff reads as a rename. The cost is a
  file that is not quite alphabetical after renames; the review page and
  `jadpo approval` say "renamed" either way.

### Versioning

- **One number per kind**, starting at 1. Any change to what a kind's
  record holds or how it is laid out bumps that kind's number, additions
  included. A view is compared byte for byte, so two compilers writing
  different additions would each call the other's file out of date; the
  manifest's "additions keep the number" rule does not fit a committed
  file.
- **A newer Jadpo, older view:** the view is out of date like any other;
  the compiler upgrade's own change runs `jadpo records update` and commits
  the rewritten views (area 18 already says to upgrade the compiler in its
  own change).
- **A newer Jadpo, older ledger:** it reads every ledger format it has ever
  written, forever, and writes the newest. Ledgers hold history and cannot
  be recomputed.
- **An older Jadpo, newer file:** `record.format_newer` names the file, the
  format it found and the Jadpo version that writes it, and stops. It never
  guesses.

### Writing, reading and checking

- **Writing** is a straight serialisation from the graph, as
  `crates/jadpo-check/src/routes/record.rs` already does for the API record:
  sorted maps in, one string out, cached per record in the query database.
- **Views are checked by regenerating and comparing bytes**, after turning
  CRLF into LF. Comparing with what the *before* side would generate (area
  18's base build, already cached) tells the two errors apart:
  - equal to the before side's text: `record.out_of_date`, the source moved
    and the record did not; `next:` names the command (agent);
  - equal to neither: `record.edited`, a hand edit or a bad merge; `next:`
    names the same command, which overwrites it (agent).
  These generalise area 7's `api.record_out_of_date`.
- **Ledgers are parsed**, one line at a time with a split on spaces and
  Jadpo's string rules; type expressions are kept as text and never parsed,
  so the reader needs no Jadpo parser. Each ledger is checked three ways:
  every line parses and appears once; the file equals its own canonical
  rewrite (order, layout); and every line added or changed since the before
  side is one its command could have written. A registry line must name
  something that existed under its born name on the before side and exists
  now under its new name; a translation line's `wording` must be the
  current wording's hash. An invented line is `record.edited`.
- **Two surfaces are compared by parsing both.** A provider upgrade is a
  new folder (`stripe/v2024_06_20/` to `stripe/v2025_01_01/`), which git
  shows as a new file, so `jadpo package update` and `jadpo approval` diff
  the parsed surfaces by entry and fact, not by line.

### Merges

- **Views:** two branches changing different routes or types touch
  different lines and merge cleanly. Two additions at the same sorted place
  conflict, and the resolution is always the same: take either side, then
  run the record's command, because the view is a function of the merged
  source. `record.edited` says exactly that. There is no line every change
  touches (no counter, total or digest), which is why open question 1
  proposes dropping the API record's `version:`.
- **Ledgers:** one line per entry, so git's built-in `union` merge keeps
  both branches' lines without conflict markers. `jadpo check` then sorts
  them back into place, and two lines for one key (one thing renamed two
  ways on two branches, one package locked at two versions) is an error
  naming both, which a person resolves. Open question 4.

### Size

An estimate for Stripe's surface: 40,000 to 60,000 lines, a few megabytes.
That is fine for git and for editors, because the grammar has no
multi-line constructs and every line is tokenised alone. Nobody reads it
whole: a reviewer reads the upgrade's surface diff, an agent runs `jadpo
package show stripe payment_intents.create` or greps headings (`rg
'^operation payment_intents\.'`), and the editor's outline lists every
entry. Splitting a surface per resource was considered and rejected: one
file per package is what "read the surface first" relies on, and the diff
is the same size either way.

## The records in full

Hashes and digests are shortened with `…` on this page only.

### The API record: `api/main.jadpo_record`

Three routes, the types they name and their failures. The heading of each
entry is its identity; every other fact is a line of its own, so a route's
failure codes no longer repeat their statuses (the status lives once, on
the failure).

```text
// Generated by Jadpo from the routes of API main; update it with `jadpo api update`, never by hand.
record api 1

api main
    idempotency required

POST /todos
    authentication none
    input CreateTodo (body)
    output TodoView
    status 201

GET /todos/{todo_id: Uuid}
    authentication none
    output TodoView
    status 200
    fails todo_not_found

PATCH /todos/{todo_id: Uuid}
    input UpdateTodo (body)
    output TodoView
    status 200
    fails todo_locked
    fails todo_not_found

input CreateTodo
    title: Text { min_length: 1, max_length: 200 }

input UpdateTodo
    done: Bool optional
    title: Text { min_length: 1, max_length: 200 } optional

output TodoView
    done: Bool
    id: Uuid
    title: Text { min_length: 1, max_length: 200 }

failure todo_locked
    status 409
    message "This todo is locked."

failure todo_not_found
    status 404
    message "Todo not found."
    todo_id: Uuid
```

- Facts in a route, in order: `authentication`, `input`, `output`,
  `status`, `fails` (area 14's section order). `authentication none` appears
  only when anyone may call the route, as built.
- An enum is `enum Name` with one fact per variant (`variant shipped`), and
  a variant's fields one indent deeper, as built.
- No `version:` line and no file pointers: open questions 1 and 2.

### The identity registry: `database/identities.jadpo_record`

Two renames: the entity `Todo` became `Task`, and its field `priority`
became `importance`. Each line is the kind, the born name, `->` and its own
name now. Children follow their parent: the field's line gives only the
field's new name, so renaming the entity again never touches it, and
fields of `Task` other than `importance` need no line.

```text
// Generated by Jadpo from renames; update it with `jadpo rename` or `jadpo domain`, never by hand.
record identities 1

entity Todo -> Task
field Todo.priority -> importance
```

Renaming `Task` again to `Job` changes the first line in place, because it
is sorted by the born name `Todo`.

### Translation sources: `domains/shipping/translations/sources.jadpo_record`

One line per locale and member: the hash of the default wording it was
translated from (`from`), the hash of its own wording when that was
recorded (`wording`), and `accepted` once a person has accepted that
wording (only with `review: TranslationReview.required`).

```text
// Generated by Jadpo from this folder's translations; update it with `jadpo translations update`, never by hand.
record translations 1

translation de_de.order_shipped from 3f9a1c0e2b7d wording 77b2e1d4c8a9 accepted
translation de_de.parcels from 0b4e7a9d1c22 wording 5e8f13a07d6b accepted
translation fr_fr.order_shipped from 3f9a1c0e2b7d wording a01c9e44f3b8
translation fr_fr.parcels from 0b4e7a9d1c22 wording 6d2a8b0e95c1 accepted
```

- **Stale** is computed, never stored: `from` differs from the hash of
  today's default wording.
- **Changed** is computed too: today's wording's hash differs from
  `wording`. `jadpo translations update` then records the current default
  as `from` and drops `accepted`; `jadpo translations accept <locale>` adds
  it back.
- A hash covers the member's whole canonical text, every variant and
  plural form, as the formatter writes it. In the root `translations/`, a
  package's member is `translation fr_fr.postcodes.invalid_postcode`, and
  `from` hashes the package's own default wording.
- `fr_fr.order_shipped` above is waiting for review, which the approval
  report lists.

### A provider package surface: `packages/acme_couriers/v1/surface.jadpo_record`

Two operations, one with a wrapped response and a field decoded from the
wire, and one event. A section with nothing in it (`provides`, actions,
polls, functions) is left out.

```text
// Generated by Jadpo from this package's code; update it with `jadpo package check`, never by hand.
record surface 1

package AcmeCouriers.v1
    /// Book and track parcel collections with Acme Couriers.
    file package.jadpo
    kind provider
    version 1.4.0
    licence Apache-2.0
    jadpo 0.6
    guide GUIDE.md

provider
    file provider.jadpo
    protocol json_http
    host live https://api.acme-couriers.example
    host sandbox https://sandbox.acme-couriers.example
    credential bearer
    idempotency header Idempotency-Key
    webhooks hmac_sha256 header Acme-Signature
    setting account_region: AcmeRegion

operation bookings.create
    /// Books a collection slot for one parcel.
    file resources/bookings.jadpo
    request POST /v1/bookings
    input CreateBooking
    output Booking
    changes
    idempotent
    fails PostcodeNotServed
    fails SlotTaken
    source written https://docs.acme-couriers.example/api#create-booking
    confirmed recordings/bookings.create.json

operation bookings.get
    /// One booking, with its collection time once a driver is assigned.
    file resources/bookings.jadpo
    request GET /v1/bookings/{id}
    input GetBooking
    output Booking
    output_at "booking"
    source written https://docs.acme-couriers.example/api#get-booking
    confirmed recordings/bookings.get.json

event BookingCollected
    /// A driver collected the parcel.
    file events/booking_collected.jadpo
    webhook booking.collected
    booking_id: Text
    collected_at: Instant (wire unix_seconds)

type AcmeRegion = Enum
    /// The Acme region the account belongs to.
    file types/acme_region.jadpo
    variant eu
    variant uk

type Booking = Object
    /// A booked collection.
    file types/booking.jadpo
    collect_at: Instant (wire unix_seconds)
    id: Text
    weight: Decimal { scale: 2 } (wire text)

type CreateBooking = Object
    /// What booking a collection takes.
    file types/create_booking.jadpo
    postcode: Text
    slot: Text

type GetBooking = Object
    /// Which booking to read.
    file types/get_booking.jadpo
    id: Text

failure PostcodeNotServed
    /// Acme does not collect from this postcode.
    file failures/postcode_not_served.jadpo
    kind rejected
    code postcode_not_served
    message "Acme does not collect from this postcode."

failure SlotTaken
    /// The slot was taken before the booking reached Acme.
    file failures/slot_taken.jadpo
    kind conflict
    code slot_taken
    message "The collection slot is no longer available."

recipe book_on_dispatch
    /// Books a collection when an order is dispatched, and records the booking.
    file recipes/book_on_dispatch/
```

- **Wire and output types both show:** `output_at "booking"` says the
  answer is unwrapped, and `(wire unix_seconds)` says how a field arrives.
  A whole-response decoder would add `wire_output ColumnTable` and `decode
  tables.to_rows`, as the decoding section of the packages page sketches.
- **A container** replaces the `host` lines with `runs image
  gotenberg/gotenberg:8@sha256:…`, `runs port 3000` and one `runs asks` per
  host it may reach.
- **Capabilities:** a mail package adds `provides email
  provides/email.jadpo` after `provider`.
- **Package actions** (`action start_subscription`) list `calls
  subscriptions.create` per operation, with `changes` beside those that
  change something; polls give `operation`, `every` and `emits`.
- `file` is relative to the package folder and has no line numbers, which
  would change with every edit above the declaration.

### A library package surface: `packages/postcodes/v2/surface.jadpo_record`

```text
// Generated by Jadpo from this package's code; update it with `jadpo package check`, never by hand.
record surface 1

package Postcodes.v2
    /// UK postcodes: reading, normalising and checking them.
    file package.jadpo
    kind library
    version 2.1.0
    licence MIT
    jadpo 0.6
    locale en_gb

function uk.normalise
    /// Writes a postcode in its standard form: upper case, one space before the inward code.
    file libraries/uk.jadpo
    signature (postcode: UkPostcode) -> UkPostcode

function uk.parse
    /// Reads a UK postcode, accepting any spacing and case.
    file libraries/uk.jadpo
    signature (text: Text) -> UkPostcode
    fails InvalidPostcode

message PostcodeHint
    /// Shown under a postcode field, with an example for the user's region.
    file translations/postcode_hint.jadpo
    example: Text

type UkPostcode = Text
    /// A UK postcode in standard form, such as "SW1A 1AA".
    file types/uk_postcode.jadpo
    max_length: 8
    min_length: 5

failure InvalidPostcode
    /// The text is not a UK postcode.
    file failures/invalid_postcode.jadpo
    kind invalid_value
    code invalid_postcode
    message "That isn't a UK postcode."
```

- A scalar type's members are its constraints, written as fields because
  that is how source writes them; a scalar type has no fields to confuse
  them with.
- `signature` holds the parameters in written order and the result; each
  failure is its own `fails` line, so a new failure, the change that most
  often breaks callers, is one added line.
- `locale` lists the locales the package words; messages and failures
  are in the surface because changing their fields breaks an app's
  rewording (area 10).

### The lock: `jadpo.lock`

The lock keeps its name, so people and tools find it where lock files
usually are, but is written in this format as a ledger, one line per
package:

```text
// Generated by Jadpo from the installed packages; update it with `jadpo package add`, `update` or `remove`, never by hand.
record lock 1

package AcmeCouriers.v1 version 1.4.0 git github.com/acme/acme-couriers commit 9c2f41d07a… digest sha256:5be1c0…
package Postcodes.v2 version 2.1.0 git github.com/acme/acme-postcodes commit 4be0d9c7e1… digest sha256:e3b0c4…
```

- `git <repository>` is the source today; `registry` takes its place when
  there is one, which is the room the packages page leaves.
- `jadpo package link` writes `package AcmePricing.v2 link ../acme-pricing`;
  `jadpo build` for production and CI refuse it.
- Lines are long (full commit and digest), as go.sum's are. The lock is
  read by tools; people read the surface diff.

## Editors and GitHub

### VS Code

The extension in `editors/vscode` gains a second language, still with no
parser of its own:

```json
{
  "contributes": {
    "languages": [
      {
        "id": "jadpo-record",
        "aliases": ["Jadpo record"],
        "extensions": [".jadpo_record"],
        "filenames": ["jadpo.lock"],
        "configuration": "./record-language-configuration.json"
      }
    ],
    "grammars": [
      {
        "language": "jadpo-record",
        "scopeName": "source.jadpo-record",
        "path": "./syntaxes/jadpo-record.tmLanguage.json"
      }
    ]
  }
}
```

**Highlighting.** Every rule is a single-line `match`, chosen by the line's
first characters, so a 50,000-line surface tokenises line by line with no
state. Values include `source.jadpo#strings`, `#numbers` and `#types`, so
records and source colour types, strings and numbers alike.

| Part | Example | Scope |
|---|---|---|
| Header line | `// Generated by Jadpo …` | `comment.line.double-slash`, the command inside as `markup.inline.raw` |
| `record` line | `record surface 1` | `keyword.other.record`, `entity.name.tag`, `constant.numeric` |
| Heading keyword | `operation`, `type`, `failure`, `entity` | `storage.type` |
| HTTP method and path | `PATCH /todos/{todo_id: Uuid}` | The `.jadpo` route-path rules: `keyword.other.http-method`, `string.unquoted.path`, `variable.parameter` |
| Heading name | `bookings.create`, `Booking`, `todo_not_found` | `entity.name.function`, `entity.name.type`, `entity.name.tag` |
| Description | `/// Books a collection slot …` | `comment.line.documentation`, dim in most themes, so reviewers skim past wording |
| Field name | `collect_at:` | `variable.other.property` |
| Fact keyword | `status`, `fails`, `file`, `host` | `keyword.other` |
| Flag | `changes`, `idempotent`, `accepted` | `constant.language` |
| File pointer, URL | `types/booking.jadpo` | `string.unquoted.path`, made clickable by the server (below) |
| Digest, hash | `sha256:5be1c0…`, `3f9a1c0e2b7d` | `constant.other.digest` |
| Arrow | `->` | `keyword.operator` |
| Anything unrecognised | | `invalid.illegal`, so a hand edit shows red |

The fact keywords for each kind are a closed list, written once in the
compiler. `tools/editor_grammar.py` gains a check, as it has for the
lexer's words, that the grammar names exactly those keywords.

**Folding.** The language configuration sets `"folding": { "offSide": true
}`, so VS Code folds by indentation and a blank line belongs to the next
entry, not the last; "Fold All" leaves a list of headings, which is the
outline of a whole API or package.

**`jadpo lsp` serves records too**, from the same parse the checks use:

- the `record.out_of_date` and `record.edited` errors on the file, with a
  quick fix that runs the record's command;
- document symbols, so the outline view and breadcrumbs list every entry;
- document links on `file` facts, and go to definition from a name in a
  view to its declaration;
- folding ranges for each run of entries of one kind, so all 1,200 of
  Stripe's types fold into one line;
- hover on a heading showing the declaration as Jadpo, as hover in source
  does.

Records open read-only through `files.readonlyInclude` if the extension can
set it as a default (to check during the build; otherwise the README says
how).

### GitHub

GitHub highlights only languages Linguist knows. Jadpo is not one, and
Linguist adds a language only once it is used in a few hundred
repositories, so for now `.jadpo` and `.jadpo_record` show as plain text.
The format is designed for that: like the CLI design language's rule that
output reads the same without colour, nothing in a record relies on colour.
Mapping the extension to another language with `linguist-language` would
mis-colour it (YAML reads `{` as a mapping; most C-like grammars choke on
`/todos/{todo_id: Uuid}`), so it is left alone. Linguist uses TextMate
grammars, so the grammar above is also what will one day colour Jadpo on
GitHub.

`jadpo new` writes these lines into the project's `.gitattributes`:

```text
*.jadpo_record                       text eol=lf linguist-generated=false
jadpo.lock                           text eol=lf linguist-generated=false merge=union
database/identities.jadpo_record     merge=union
**/translations/sources.jadpo_record merge=union
```

- `eol=lf` keeps the bytes the compiler compares the same on Windows
  checkouts (the compiler also ignores CR when comparing).
- `linguist-generated=false` keeps every record's diff expanded in pull
  requests. Generated files are usually collapsed; records are committed so
  that their diff is read.
- `merge=union` is git's own driver and needs no configuration on a
  developer's machine. Whether GitHub's merge button applies it is still to
  be checked; if not, the pull request shows a conflict and the developer
  merges locally, where it applies.
- Hunk headers: git's default picks the nearest line above a hunk that
  starts with a letter, which is an entry's heading here (descriptions
  start with `/` and facts are indented). So GitHub shows the entry either
  in the hunk header or in the hunk's own context lines.

## How diffs read

**An API change.** A route gains a failure, and an output gains a field:

```diff
@@ -20,6 +20,7 @@ PATCH /todos/{todo_id: Uuid}
     input UpdateTodo (body)
     output TodoView
     status 200
+    fails todo_archived
     fails todo_locked
     fails todo_not_found
 
@@ -32,9 +33,14 @@ input UpdateTodo
 
 output TodoView
     done: Bool
+    due_on: Date optional
     id: Uuid
     title: Text { min_length: 1, max_length: 200 }
 
+failure todo_archived
+    status 409
+    message "This todo is archived."
+
 failure todo_locked
     status 409
     message "This todo is locked."
```

The second hunk's header names `input UpdateTodo`, the heading above the
hunk; the entry it changes, `output TodoView`, is in its first lines.

**A rename.** `jadpo rename Task Job` changes one registry line. Renaming
a type the API names changes its heading and the lines that name it, in
place, because the entry stays where its born name sorts:

```diff
-entity Todo -> Task
+entity Todo -> Job
 field Todo.priority -> importance
```

**A re-translation and its acceptance.** The German subject was reworded
after the English changed; `jadpo translations update` records it, then a
person runs `jadpo translations accept de_de`:

```diff
-translation de_de.order_shipped from 3f9a1c0e2b7d wording 77b2e1d4c8a9 accepted
+translation de_de.order_shipped from 8e21f07a6c43 wording c4d05b9e1a72 accepted
```

On the branch before acceptance, the line has no `accepted`; the reviewer
who owns the file sees it appear.

**A library upgrade.** `jadpo package update postcodes` takes 2.1.0 to
2.2.0, in the same `v2` folder, so the surface diff is a git diff:

```diff
@@ -5,7 +5,7 @@ package Postcodes.v2
     /// UK postcodes: reading, normalising and checking them.
     file package.jadpo
     kind library
-    version 2.1.0
+    version 2.2.0
     licence MIT
     jadpo 0.6
     locale en_gb
@@ -15,6 +15,11 @@ function uk.normalise
     file libraries/uk.jadpo
     signature (postcode: UkPostcode) -> UkPostcode
 
+function uk.outward_code
+    /// The outward code of a postcode: "SW1A" in "SW1A 1AA".
+    file libraries/uk.jadpo
+    signature (postcode: UkPostcode) -> Text
+

     /// Reads a UK postcode, accepting any spacing and case.
     file libraries/uk.jadpo
```

with the matching lock line replaced. A provider's new API version is a
new folder, so its review is `jadpo package update`'s surface comparison,

PostcodeNotServed on bookings.create`.

## Open questions

1. **Should the API record keep its `version:` counter?** Every change
   bumps it, so two branches that both change the API either conflict on
   that line or, when both wrote the same number, merge silently and fail
   `check` until someone reruns `jadpo api update`. *Recommendation:* drop
   it. The OpenAPI document's `info.version` becomes the first 12 hex digits
   of the record's SHA-256, computed at build and never stored. Clients
   compare documents, not counters; if an ordered number matters to a
   client team, it can be added later as the count of accepted breaking
   changes, which changes rarely and only with a person involved.
2. **Should the API record point at source files?** *Recommendation:* no.
   Moving a route group or promoting a type to `shared/` would change a
   file that CODEOWNERS protects, for no change to any client; the editor's
   go to definition and `jadpo inspect` find the source from a name. Package
   surfaces keep their pointers: a package's files are fixed per version.
3. **How much of a description goes into a surface?** *Recommendation:* the
   first paragraph, joined onto one `///` line. Whole descriptions carry
   the required examples, which would make surfaces several times longer
   and turn every documentation edit into upgrade noise; `jadpo package show
   <name> <declaration>` prints the whole description.
4. **Should ledgers merge with git's `union` driver?** *Recommendation:*
   yes, for the registry, translation sources and the lock, because their
   one-line entries make it safe and `jadpo check` catches every case it
   gets wrong (a duplicate key, an invented line). The alternative is
   conflict markers on every pair of branches that both rename or both
   translate.
5. **Should `jadpo.lock` use this format?** *Recommendation:* yes, keeping
   its name: one grammar, one highlighter, one parser and one check for
   every file Jadpo commits, and the lock's needs (sorted, one line per
   entry, merged by union, format-numbered) are exactly a ledger's. It is
   not built yet (chunk 7.1), so nothing migrates.
