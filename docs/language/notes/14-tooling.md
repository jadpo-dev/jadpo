## Decisions

| Topic | Decision |
|---|---|
| How `jadpo suggest` finds a published copy | Recommended 2026-11-08 (R8, built unattended; to confirm): by the release's own `source` fingerprint, the similar-helper check's likeness, so there is one scheme; a `shape` match was rejected, since `(Text) -> Text` is shared by hundreds of unrelated functions and a distinctive shape is rare enough to find nothing. The registry is asked with each fingerprint's first five hex digits (`POST fingerprints/query`, a new row of the protocol) and answers the whole bucket, k-anonymity as Have I Been Pwned's range API does it, so it learns nothing of which functions an app holds; sending whole fingerprints was rejected because it would tell the registry exactly which published functions an app copies. It asks by default, since an agent never passes a flag it doesn't know about, `JADPO_SUGGEST_REGISTRY` (anything but `on`) stops it on a machine or in CI, and the teaching-example gate runs with it off so its answer doesn't change with what is published; a `suggestions { registry: false }` option was left out until a project asks, which also keeps the `suggestions` errors' pages as they are. An unreachable registry, or one that doesn't serve the row yet, never fails the scan: the summary says `registry not reached`, and a `published` finding missing from that scan isn't counted taken nor its ignore dropped. The suggestion is the package and declaration, `@acme/postcodes uk.parse`, as `jadpo package search` lists a result, so the ignore record reads a suggestion up to its quoted reason, which every earlier record still reads as before |
| How `jadpo suggest` finds a standard function | Recommended 2026-11-08 (R8, built unattended; to confirm): a standard operation is built in, with no source to fingerprint, and the registry indexes the standard library's types, not its functions, so the scan matches it locally from the operation table: the function's own name is the operation's, word for word with or without the namespace (`slug`, `text_slug`), and each parameter and its result fit the operation's kinds. A name holding more words (`count_active`) is left alone, since a function named for more than the operation usually does more; a shape alone, with no name, was rejected for the noise above. It is the `function` signal, beside `published` |
| Which release `jadpo package check` compares with | Decided 2026-11-07 (Richard): `check` counts releases from git tags and the registry counts what it published, so a tag the registry never took (a release its verifier refused) made `check` write a "changes since" section the registry refused for a first release. `--previous <version>` names the tagged release the registry holds and `--previous none` a first release, as `verify --previous` names the release before. Asking the registry from `check` was rejected: `check` runs in a package's CI before a tag, and has to give the same answer with or without a network |
| A Workers deployable | The files sit side by side in `build/target/<deployable>/` (`<deployable>.wasm`, `<deployable>.js`, Jadpo's `worker.mjs` and `wrangler.json`), uploaded unbundled by explicit rules; its compatibility date is the one the Workers host is tested at, moved with the pinned workerd; each setting without a default is a required secret, since Wrangler names a binding without its value no other way, and one with a default is left out; sizes are decimal and gzipped at zlib's default level, as Wrangler reports an upload |
| A deployable's release profile and its Worker's name | Each deployable's workspace gives its release profile, fat link-time optimisation in one codegen unit, `opt-level = 3` natively and `opt-level = "s"` for Workers, so the module measured is the one that ships, at the cost of a rebuild taking half a minute to a minute where it would take seconds; a Worker's module is bound without its name section or `producers` section, and a native binary keeps its symbols, which have no upload limit to meet and which a backtrace and a profiler read; the Worker is named `<app>-<deployable>`, the app's name its folder's until `app.jadpo` gives one, both lower-cased with each run of anything but a letter or digit one dash and at most 63 with the deployable's kept whole, so two apps' `kiosk`s are two Workers in one account; the Wrangler file is built as one value, every binding a field; and it enables Workers Logs, `observability: { enabled: true }`, which the pinned Wrangler leaves off unless the file says so, since this page promises Workers Logs reads the log |
| A Worker's start | An isolate starts at its first request, reading its settings from the bindings and checking `client_address:` once, a failure logged once and every request of the isolate answered 503 `unavailable`, since a Worker's bindings change only with a new version; its stores' migrations compared at each request until they are current and not again for the isolate, a store behind, ahead or out of reach answered 503 and logged each time, so a migration applied after a deploy is picked up without one; `runtime.started` logged once an isolate is current; the log on the console, one JSON line an event; the HTTP component's per-worker state (request numbers, the readiness check reused for a second) kept per isolate; a `client_address:` source other than `cloudflare` stops the start as `client_address_refused`, and `jadpo check` refuses it first |
| A Worker's database | The Wrangler file writes each database's address setting as a Hyperdrive binding in place of a required secret (area 5, "PostgreSQL through Hyperdrive"); its `id` is read from the build's environment, `JADPO_HYPERDRIVE_<variable>`, a tool's variable as `JADPO_WORKERD` is, since the id differs for each Cloudflare account and environment and isn't the app's to hold in source; without one the binding is written without an id, which `wrangler deploy` refuses, and the screen's `database` line says `no id` with an alert to create one with caching off, the one thing a Worker can't check itself |
| What `jadpo check` and `jadpo build` say for Workers | A `client_address:` source other than `cloudflare` is `deployable.target_unsupported`, one more thing a target can't run, rather than a rule of its own, at its `source:` with the deployable's `target:` beside it, once for each Workers deployable, any deployable on Workers being held to it since the Worker's start refuses it whatever it serves; a `client_address:` with a problem of its own is reported as that alone; the build screen says a Worker's caps on calls as one field, `calls`, after what it serves and runs, rather than repeating `jadpo check`'s "On Workers" section, since `jadpo build` checks first and each Worker's block is where its facts are read |
| Six connections an invocation | An invocation's connections are counted as Cloudflare counts them, six waiting for their answer's head at once (a `fetch()` until its status and headers come, a `connect()` until its socket opens), not six held open, which would hold a seventh behind a store's idle connections; the runtime counts them itself, since workerd counts none and a seventh left to the platform's queue runs out its timer unseen; the six are shared by everything one invocation opens (its drivers, its own fetches, the work it leaves in `waitUntil`); a seventh waits in the order asked, within its own timeout, and one whose timeout passes first is `NotSent`; the service binding work is handed on through, the rate-limiting binding and `startTls()` aren't counted, as Cloudflare's list leaves them out; `max_concurrent:`'s slots are the isolate's, a slot given back handed to the longest-waiting call, which looks for it every 10 ms on its own invocation's timer, so no invocation wakes another's work, and a holder that hasn't said it is there for five seconds, beating every second, is forgotten, as is a waiter that hasn't looked, since Workers ends an invocation whose client went away without dropping what it held |
| What a deployable keeps of sign-in, and logs of its ticks | A deployable keeps who signs in (the principal, the session and key stores, the passkey and magic-link plans an action's own route may call), but a method's signing key only where it serves an API that takes the method and the browser session's origin only where it serves one that takes browser sessions, so one serving no such API neither needs nor reads them; the magic-link email still reads the origin where subscribers run, since its link is built from it. Every tick is logged as `runtime.ticked`, a server's own timer's and a Worker's cron's as well as `<deployable> tick`'s, even one that did nothing, so a store a tick can't work in is seen wherever it ticks; a tick a stop cut short logs nothing, the `runtime.stopped` that follows saying why |
| Where deployables are compiled | `jadpo build` compiles every project's deployables into cargo targets shared by them all (docs/compiler-runtime.md §2.5, "Keeping rustc time down"), in `jadpo/builds/<version>-<copy>/` of the user's cache folder (`<copy>` a digest of where the running `jadpo` is), where the package cache is (`$XDG_CACHE_HOME`, else `~/.cache`; with neither, the project's `build/rust/cache/`), one target for each host, locale data and set of cargo's `CARGO_PROFILE_RELEASE_*` overrides, and the locale data in a folder named by its digest, written whole and renamed into place; so only an app's own crates compile after Jadpo's first build of a host and locale set, rather than every app's first build being a cold release build. A build holds the target's lock until it has copied out what it built, and marks its files changed when another project last built a deployable of its name, so builds at once and builds of two projects never take each other's program. Nothing prunes the cache yet; deleting it costs a rebuild |
| Building outside this checkout | A released `jadpo` carries the runtime crates' source, packed into the binary at its build (their manifests without what only their own tests read, beside a workspace manifest of their own), written into `jadpo/runtime/<version>-<copy>/` of the cache folder, a file left alone when its bytes are unchanged so cargo rebuilds only what changed; and fetches the pinned Rust toolchain from Rust's dist server as rustup does, the `.tar.gz` archives (the `.tar.xz` ones, a third smaller, would need liblzma or another decoder), the manifest checked against the SHA-256 this Jadpo pins and each archive against the manifest's, a mirror named by `JADPO_RUST_DIST_SERVER` trusted for its manifest's `.sha256` as rustup trusts `RUSTUP_DIST_SERVER`'s; crates come through cargo from crates.io, pinned by the lock, fetched only when an offline resolve or fetch fails, so a warm cache never touches the network. Rejected: vendoring every crate into the binary, hundreds of megabytes for each release; and shelling out to rustup, which a machine without Rust hasn't got (for fetching the toolchain; chunk 9.2c for the rest) |
| A deployable's target when none is declared | An app with no `deployables:` has no target until one is asked for: `jadpo check` refuses no driver by target, and `jadpo build` builds native; a target is checked once a deployable declares one, or a build asks for Workers |
| Formatting | Carried from area 1: the formatter owns blank lines and section order within a file |
| Promotion | Carried from area 1: required with a one-step fix, applied through the editor or `jadpo fmt --layout`, never on save; demotion never forced |
| Helpers | Carried from area 1: descriptions written once as `///`; the library catalogue, callers and `jadpo impact` are computed; similar helpers flagged by `jadpo check` |
| Domain commands | Carried from area 1: `jadpo domain rename`, `split` and `merge` move files and update every call; a new or renamed domain appears in the approval review |
| Documentation comments | Carried from area 1: `///` feeds generated docs, the library catalogue and OpenAPI |
| Failure catalogue | Carried from area 4: the compiler generates a catalogue of every failure |
| Migration workflow | Carried from area 5: `jadpo migrate new` / `apply`, one migration per store, check fails on drift, the app refuses a mismatched database |
| Schema report | Carried from area 5: the build includes a report of every table, column and index with the query that needs it |
| Seeds | Carried from area 5: `jadpo seed <name>` runs a seed through the application's actions and refuses production |
| Route listing | Carried from area 7: hover shows a route's full path; `jadpo routes` lists every route |
| Query SQL | Carried from area 6: `jadpo sql <query>` (with `--explain`) and an editor hover show a query's generated SQL; never written into source |
| Write SQL | `jadpo sql <action>` also shows the statements an action's writes send, each with its parameters and the conflict arm each constraint maps to |
| Permissions report | Carried from area 9: the build writes `build/report/permissions.md` and a `.json` twin, a matrix of who can do what to every entity and field; changes to it appear in the approval review |
| Optional project path | Every command finds the project by walking up to `app.jadpo` from the current folder and accepts a path, `config` included, as Cargo, npm and Go do, so agents never guess which form a command takes |
| `--json` | One `--json` on every non-interactive command, so each has one machine form; plain text when piped, colour otherwise |
| `check` writes derived files | `check` writes `build/` except the runnable app, so the catalogues an agent reads are never stale; `build` adds `target/`; `dev --no-run` only rebuilds; one command per job |
| `migrate` commands | `jadpo migrate new <purpose>` writes the migration folder with its SQL for review and keeps `database/identities.json` current; `apply` runs it; `status` lists pending ones. The latest migration is the snapshot, decisions live in `changes.jadpo`, checked by `jadpo check`, and there are no snapshot, diff, decision-file or index commands (area 5): generate, review, apply |
| Renaming | `jadpo rename <old> <new>` updates source, callers, file names and the identity registry in one step; the editor's rename calls it; a hand rename of stored data shows as a removal and an addition, which `migrate new` refuses with a pointer to the command; domains keep their own `jadpo domain` commands because they move folders |
| Renaming a name in use | `jadpo rename` refuses a new name already in use before editing anything, naming the declaration that holds it and its file, and lists the names in use that contain the same word, as `semantic.duplicate_declaration` does; a name is in use where the new name would have to be unique: in the domain for a private function or type, across the project for everything else |
| What `jadpo rename` renames, and how it is named (chunk T1) | Chosen 2026-11-10, the page being silent on its scope: entities, types of every kind, functions, constants, actions, queries, fixtures, seeds, schedules, subscribers, libraries and a library's functions and constants, and the fields and variants of an entity or a type. The old name is looked up as `jadpo impact` looks one up; a field is named after its owner (`Todo.priority`) and its new name is its own (`importance`) or after the same owner (`Todo.importance`), since a rename keeps a field where it is; another owner is refused. A domain is refused, naming the `jadpo domain rename` it needs, since it moves a folder; a route goes by its method and path and a test by its sentence, both changed where they are written. Each refusal is `cli.rename_arguments`, a usage error (exit 2) |
| Where `jadpo rename` writes (chunk T1) | Chosen 2026-11-10: every name the find-references resolution says refers to it (now also a constant's declaration and a root `policy { actions: }` line, which it didn't resolve), and for a field also every field copied from it with `pick:` and what reads those, since a copy's name is the field's. Never a migration's folder (history, whose decisions name born names) or an installed package. The declaration's file, when named after it, moves to the new name's file with the `.test.jadpo` beside it, refused when either is taken. `use` lines are left to the diff, as `config move` leaves them |
| The registry and the records a rename writes (chunk T1) | Chosen 2026-11-10: one line for the thing renamed, keyed by its born name; a second rename changes it, a rename back to the born name removes it, and an entity, type or library renamed carries its members' lines in memory (the file's member lines give only their own names, so they don't change). The view records the rename puts out of date (API, event, access, network) are written again, as `jadpo records update` writes them, so the rename leaves `jadpo check` as it found it; whether the change needs a person's acceptance stays `jadpo check`'s to judge against the before side, and the screen's hint says so whenever such a record was written. *Rejected:* leaving them out of date for `jadpo records update`, which would make every rename of an action or entity end with a failing check |
| A rename never adds an error (chunk T1) | Chosen 2026-11-10, as `jadpo fix` does: a result with an error the project didn't have, by rule and headline, is undone and shown (`rename stopped`); errors the project already had stay and are counted in the hint; a file that doesn't parse stops it first. This is what keeps data that the registry doesn't yet keep from being lost silently: a change `jadpo migrate new` would have to make shows as an error and stops the rename. Its screen is `config move`'s change list, then `Renamed <name> to <new>` with a `kept` row naming the table or column kept for an entity or an entity's field |
| A born name is a name in use (chunk T1) | Chosen 2026-11-10, for `jadpo rename`: a new name that another declaration or member of the same kind was born with is refused, since stored records and the review know that one by it, and names now and born names sharing one spelling would make a key's lookup by name ambiguous (a root policy line is found by either). **Recommended, for Richard to confirm:** `jadpo check` should refuse the same for a declaration written by hand, a new `greet` while `welcome` was born `greet`, since its key would be `welcome`'s; not built, as the area pages don't yet say it |
| What `jadpo domain` takes (chunk T2) | Chosen 2026-11-11, the pages naming the three moves but not their arguments: `jadpo domain rename <domain> <new-name>`, `merge <domain> <into>` and `split <domain> <new-domain> <name>...`, the names being declarations of the domain as written. A split moves each named declaration's file whole, with the `.test.jadpo` beside it and what is named after it in its folder (an email's templates, a prompt's text and recordings). *Rejected:* a split that pulls in everything the named reach, which can move far more than was named without saying so; instead the refusal names the command that moves all of it |
| A split's seam (chunk T2) | Chosen 2026-11-11, from area 1's "only along a seam the compiler shows has no references across it": any graph edge between a file that moves and one that stays, either way, tests counted with the file they sit beside, refuses the split, naming the first three references and how many more. When what the named reach together still leaves part of the domain, the next step is the split that moves all of it; when it is the whole domain, the next step is to keep it one domain, as area 1 says of a domain whose parts depend on each other. Naming the whole domain is refused toward `jadpo domain rename` |
| A domain's own files in a split (chunk T2) | Chosen 2026-11-11: `monitoring.jadpo`, the language files in `translations/` and any file at the domain's root stay with the domain split, as they belong to no one declaration; a split whose thresholds or wordings name what moves stops with the error it would leave. Dividing them is not built yet |
| What a merge changes in code (chunk T2) | Chosen 2026-11-11: every file moves to the same place in the other domain; a call between the two loses its qualifier, as code calls its own domain's declarations by name, and a `use` line names the domain merged into, the imports then fixed as `jadpo fmt` fixes them. A declaration that was `public` only for the other domain is no longer `public`, since `visibility.public_unused` would otherwise make every merge of two domains that call each other fail; the change list shows each. Two files at one place or a name declared in both is refused before anything changes. *Rejected:* merging two `monitoring.jadpo` or language files, which needs a person's view of which threshold or wording wins |
| A setting that lists a domain (chunk T2) | Chosen 2026-11-11: a name in a list such as a connection's `domains: [planning]` refers to the domain, so a rename and a merge rewrite it, and a split lists the new domain beside it (`domains: [planning, notes]`), so the code that moves keeps the store and the queue it had |
| A move never adds an error (chunk T2) | As `jadpo rename` (chunk T1): a result with an error the project didn't have is undone and shown (`domain split stopped`), and the records it puts out of date are written again. The screen lists a folder that moves whole as one row, a split's moved files one by one, each line outside them that changed, and the status line's `kept` row names the tables that stay where they are, with a split's seam (`moved 4 declarations`, `stayed 5, with no reference across`) |
| Parallel agents | The agent skill's routine: merge `main`, run `jadpo check`, fix any clash, then push; generated CI runs `jadpo check` first, so a clash fails in seconds; what generates CI is not yet specified |
| Error messages | Relative paths, impact lines only when useful, repairs carry their edit, JSON line and column, help links to these pages: a short, exact message with one suggestion is what people and models act on |
| Affected tests | `check` reports which domains and tests a change reaches but runs nothing, so it stays fast enough to run after every edit; `jadpo test --affected` runs exactly those |
| What `--affected` measures against | The merge-base with `main`: the tests reaching any node whose digest differs from that commit's, read through the same before side as diffs |
| One member per line | Formatter writes one member per line and a blank line between declarations, so `fmt --check` enforces areas 2 and 3's colon and one-per-line rules; a short list such as `pick: [Todo.id, Todo.title]` stays on one line, and `include`, `pick` and `omit` lines keep the order written (area 2) |
| Section order | The formatter orders sections: a failure's `kind`, `code`, `message`, `client`, `internal`; a route's `authentication`, `confirm`, `rate_limit`, `input`, `output`, `sends`, `status`, `cache`, `deadline`, `run`; an entity's fields (in written order), then `identity`, `persistence`, `lifecycle`, `membership`, `policy`, `freshness`, `guard`, `person`; other sections follow in written order |
| Scaffold | `jadpo new` creates area 1's fixed root (`app.jadpo`, `config.jadpo`, `domains/`, `database/`, `tests/`), one small domain with an action, a route and a test, and no hidden folders, so a new project passes `check`, `fmt --check` and `test`. `app.jadpo` declares the Jadpo version the app needs, and the compiler refuses an app that needs a newer one; the project's `AGENTS.md` says what Jadpo is, that version, and where its docs are ([documentation](../../documentation.md)) |
| Catalogue form | Markdown in `build/catalogue/` and `build/report/` with `.json` twins, plus `jadpo impact` for questions about one name; agents already search files well, and an MCP server can wrap the same output later without a second source |
| Build-only errors in `check` | `toolchain.target_*` errors come from `check`, so an agent learns a feature can't run yet before writing code around it, and a project that passes `check` builds |
| Sign-off | Settled by area 7: acceptance files in a folder the git host protects; CI's `jadpo check` fails without them; no signing or user accounts of Jadpo's own ([Review and sign-off](../14-tooling.md#review-and-sign-off)) |
| Operator commands | `jadpo deliveries list`, `retry`, `dismiss`, `cancel` and `resolve <id> --done` or `--not-done`, run against an environment through its configuration, each action logged with who did it; alerts are log events the hosting platform's alerting picks up; a web screen can come later on the same operations. The states and the log are in area 12, "What an operator sees" |
| Deployables | Declared in `app.jadpo` under `deployables: { }`, each saying what it serves or runs (`serves: [main, webhooks]`, `runs: [Trigger.schedules, Trigger.subscribers]`) and its target (`Target.native` or `Target.wasm`, compiler-runtime §1); each is compiled from what it reaches; with none declared, one deployable runs everything; `jadpo build <deployable>` builds one and `jadpo dev` runs all in one process |
| Command synonyms | Plain synonyms where people reach for either word (`fmt` and `format`, `delivery` and `deliveries`, `package` and `packages`); an unknown command suggests the nearest one ("did you mean `format`?"); no cryptic single letters; help and docs show the canonical name |
| Completion and prompts | Tab completion for zsh, bash and fish (`jadpo completions zsh`) from the top level: `jadpo` and Tab lists every command with a one-line description, every flag is offered with its description, and the project's own names complete (queries for `jadpo sql`, routes, schedules, test files and test names, connections, every declaration for `jadpo impact`); a command missing a required argument opens a searchable list in a terminal and fails listing the valid values otherwise, so agents get the choices too; the CLI describes itself fully (`jadpo` alone and `jadpo <command> --help` with every subcommand, flag and an example, `jadpo help --json` with the whole command reference as data), so nobody needs the docs, which are generated from the same source |
| Incident input | `jadpo incident` reads a file, standard input, or text pasted at a prompt in a terminal; Jadpo events are found inside surrounding log text (timestamps, platform wrappers) and grouped by request; the build's manifest is found by the event's build id (area 18) |
| CLI design language | As the [CLI design language](../../cli-design-language.md) sets out: six meaning-only colours, single-width symbols with ASCII fallbacks, one layout grid, calm by default; Jadpo's own colours when the background is known, otherwise the terminal theme's; Unicode symbols, no emoji or Nerd Font glyphs |
| Translation commands | `jadpo translations missing`, `unused`, `builtin`, `update`, `accept <locale>`, `export` and `import` (XLIFF or JSON), `--json` wherever they print; go to definition from a translations call to its type and wording (area 10) |
| Package commands | `jadpo package new`, `add` (registry, git, path or URL), `import`, `record`, `conform`, `check`, `publish`, `update`, `remove`, `show`, `link`, `unlink` and `recipe`, for both kinds of package; `update` shows the difference in the operations the app uses; `jadpo packages outdated` and upgrade plans come with the registry (area 11) |
| Service, call and grant commands | `jadpo services` with `start`, `stop`, `restart`, `logs` and `shell`; `jadpo calls`, `calls show` and `calls script`; `jadpo dev grants add` (area 11) |
| Records command | `jadpo records` lists every committed record and flags any out of date (area 18) |

| Batch commands | `jadpo batches list`, `show` and `cancel` for operators; `jadpo runs unfinished --build <build id>` before a deploy; no deploy command, since a rerun detects a changed build by its build id |
| Constants for agents | The library catalogue lists library constants with their type, value, description and readers; `constant.similar_exists` flags two constants of one type holding one value; the agent skill says a value a deployment could ever need to change is `config`, otherwise a `constant` (area 3). The agent skill isn't built yet |
| Making a constant a setting | `jadpo config move <constant>`, and the editor's "Make this a setting" code action through the same code, moves a constant into `config.jadpo` and rewrites every read (area 10); offered, never required, so not part of `jadpo fmt --layout`; the agent skill points at it |
| Editor quick fixes and formatting | Every error whose next step carries edits is a quick fix titled by that step up to its "or run ..." alternative, which is the command line's; promotion's applies its edits then fixes every file's imports and lays out each touched file that was laid out, as `jadpo fmt --layout` does, so one fix leaves no import error behind; formatting runs `jadpo fmt`'s code on the editor's unsaved text, and the extension turns format on save on for `.jadpo` files by default, since the formatter owns layout |
| Find references | Each identifier of the name's spelling is resolved by the same lookup as go to definition and kept when it reaches the same node, rather than read from the graph's call and use edges, which hold no places; a parameter or variable is looked for in its own body |
| The extension's own screens | A language status item, not a status bar item of its own, naming the `jadpo` running and its version, an error severity when none is found or it didn't start; one notification per failure with the single next step as its button, none on success; "Open Generated File" is a quick pick of `build/`'s readable files by folder with a refresh button that runs `jadpo check`, since the files are as that last wrote them |
| Publishing the extension | `.github/workflows/vscode-extension.yml`, dispatched by release-please after dist's workflow, packages at the tag's version (MAJOR.MINOR.PATCH, as the Marketplace takes) and attaches the `.vsix`; publishing to the Marketplace and Open VSX waits for dist's run for the tag and the release out of draft, so the extension never asks for a `jadpo` that can't be installed, and is off until `JADPO_VSCODE_PUBLISH` is `on` |
| Which `jadpo` runs | Every installed `jadpo` is a whole `jadpo` that switches, as Go's toolchain switching does, rather than a separate thin launcher, which needs the least machinery: in a project it reads the release line from `app.jadpo`, and runs itself when it is that release, else the release `jadpo.lock` pins or the newest of the line, kept in a per-user cache or fetched from GitHub's releases. A fetched archive is checked against its published SHA-256 and its GitHub artifact attestation before it runs, the attestation with Sigstore's own Rust verifier (`sigstore-verify`, no TUF, HTTP client or C library) over RustCrypto's curves and the public-good trusted root it carries, the identity `release.yml` at the release's tag. Outside a project `new`, `--version`, `help` and the toolchain commands run with the installed version; `toolchain list` and `remove` always do. The line, not a minimum, is the compatibility unit, since a 0.x minor release may break apps; a `jadpo` that can't hand the project on refuses with an error naming the release to install, and `toolchain.version_older` is the rule for a later binary meeting an earlier line. The pin is a `jadpo version <release>` line first in `jadpo.lock`, written by `jadpo toolchain pin` and taken out by `unpin`; the lock stays `record lock 1`, since no format-1 lock shipped without it. `JADPO_TOOLCHAIN=local` runs everything with the `jadpo` started, for compiler developers. VS Code runs `jadpo lsp` from the project folder, so it needs no configuration, and `jadpo.server.path` stays only as a compiler developer's override. Built into the first release, so the first install already switches versions per project |
| Editor completion | Completion for everything as you type, generated from the declarations and data the compiler uses, never a list kept for the editor: names in scope, fields, operations with signature, failures and docs, variants with CLDR names, units after a number narrowed to the type required, named arguments, type names, declinable rules, settings, messages and keywords; snippets for calls with required arguments; no AI suggestions in the server |
| Suggestions | `jadpo suggest` hints where code could use a standard type or operation and never edits; it formats, then matches signals held as data on the standard types' entries (shape, conversion constants, name hints, format literals, validation patterns) and a loop table for operations through canonical graph fragments, numbers its findings and ends with the agent's instruction; `ignore` writes the canonical hash, signal and reason to the committed `ignored_suggestions.jadpo_record`; `found` teaches a miss; a vanished finding is accepted; everything to share waits in `.jadpo/suggest_pending` for `share` |
| Sharing with Jadpo HQ | Sharing is on unless `suggestions { share: false }` or `JADPO_SUGGEST_SHARE=off` turns it off; `share` sends the pending hashes with their kinds and a committed random project token at once, shows the snippets HQ asks for (those seen from enough distinct projects) as the exact payload, and sends them only with `--approve` after a person said yes; unattended runs send only hashes; the pending file is wiped after; taught patterns are kept in the committed `taught_suggestions.jadpo_record`; the protocol (HTTPS and JSON under `/v1/`) and HQ's agent are written on this page so the real HQ implements them unchanged |
| Watching saves | `jadpo dev` and `jadpo test --watch` look at the files every few tens of milliseconds and take a burst of changes once they have been quiet for 50 ms. A file that had text and is empty at that point is an editor's save in place, truncated and not yet written, and the burst waits for its text, however far apart the two writes are, up to 2 seconds; a file still empty then is a save. Waiting instead for every changed file's content to stay the same across a longer settle would cover only a gap shorter than the settle and slow every save, while an empty file is the one half-written state that checks cleanly; a partly written file fails to check and keeps the last good version serving |
| Settings in name order | The formatter sorts `config { }` fields by name, the one exception to fields keeping their written order, so parallel workspaces adding settings rarely clash (area 10) |
| `build/` kept out of git | `jadpo dev`, whose inbox and call log are kept in `build/`, adds `build/` to the project's `.gitignore` each time it starts and finds it not ignored there (as `build`, `build/`, `/build` or `/build/`), making the file when there is none and keeping what it held; `jadpo new` writes it too. `jadpo check` leaves `.gitignore` alone, since what it writes is derived and holds no prompts or mail |
| `jadpo inspect` and `jadpo impact` (chunk A17) | Both read the graph `jadpo check` builds, never an index of their own: `inspect` prints each domain's declarations with what each calls, runs and raises, `inspect <name>` one node with its fields and edges both ways, and `--json` the manifest or the node as the manifest has it; `impact <name>` follows the graph's edges backwards (calls, runs, reads, writes, emits, subscriptions, raises, references, includes and uses) to the calling domains, with call sites counted from the typed bodies, the entry points and the test files, a field's change counting as its type's. A name is looked up as code writes it, its whole key, or its born name with the domain when two domains share it, and a declaration wins over the placement or tenancy that goes by its entity's name. Its lines are `callers` (or `used in`), `triggers`, `tests` and `public`, labels of eight characters at most, as the CLI design language's grid asks, in place of the first transcript's `called from` and `entry points` |
| A project with errors under `inspect` and `impact` | Recommendation awaiting Richard (A17, 2026-11-08): both refuse it and show its errors, as `jadpo sql` does, since a graph built from a project with errors leaves out what couldn't be resolved, and `impact` would then understate what a change reaches with no sign of it. The alternative, answering from the partial graph with a warning line, was not taken because nothing in the output would say which edges were missing; `build/manifest.json`, which `check` writes either way, stays the place to read a broken project's map |
| `jadpo package update --plan` (chunk R9) | The candidate is fetched and verified as `update` does it, then held in a scratch copy of the project's files in memory, never a folder on disk: its folder and lock line replaced, the rest as it is. Each change record entry is followed with `jadpo impact`'s walk on the app's graph as it stands, since what the app uses is read on the before side (area 18): a type, function or operation from its own node, the package's or provider's own entry from every public operation, capability and function of the package, since a host or a raised `jadpo` reaches every call through it; an added entry reaches nothing. When [Tools](../14-tooling.md) was rewritten to the [writing

the details of how the tools themselves are built, moved here. Nothing in
this list changed a rule.

- **The page's scope.** Its commands and outputs apply the decisions of
  areas 1 to 14. The tools for agents come from areas 1, 4 and 5.
- **Where each command was specified.** `jadpo impact` and the `jadpo
  domain` commands in area 1; `jadpo seed` in area 5; `jadpo test
  --interactive` in area 13; `jadpo package new`, `jadpo services` and
  `jadpo dev grants add` in area 11; `jadpo files copy` and `jadpo search
  reindex` in area 16; `jadpo trace`, `why`, `call`, `console` and
  `incident` are proposed in area 17. `jadpo package update` prints area
  18's review of the surface the app uses, and `jadpo package add` reads
  the registry in area 11's fixed order.
- **Editor rename** waits for `jadpo rename` and the identity registry it
  writes (areas 5 and 18).
- **The acceptance form** that a breaking API change, a database drop,
  weaker policy and a new or renamed domain share was designed in area 7.
  Jadpo builds no signing or user accounts of its own, since review already
  happens on the git host.
- **Runtime events.** Area 4 decided what `runtime.unhandled_fault`,
  `runtime.outcome_unknown` and `runtime.startup_failed` log. Area 8 asks
  that a protected route with no authentication set up is reported by
  `jadpo check`, as the `toolchain.target_*` errors are.
- **The unreachable `type.job_delivery_*` errors** go with the delivery
  descriptor if area 12's question 2 is accepted.
- **Query SQL is never written into source as a comment**, because it
  would go stale, add noise to diffs and invite edits.
- **The editor's code.** Formatting in the editor runs `jadpo fmt`'s code
  through `jadpo_check::formatting`. Completion is built in
  `jadpo_check::completion`, through the checker's analysis of the text as
  it is typed, and the server's `textDocument/completion`; a test offers
  every operation each stub declares after its namespace, with no

## `jadpo test --affected` (chunk T3)

Decisions the page didn't make, recommended here and open for a
maintainer to overrule:

- **The base is the before side's commit**, found exactly as `jadpo check`
  finds it: the merge base with the default branch, and on the default
  branch itself the previous commit. "The merge-base with `main`" would
  give nothing to run on `main`, and the decision above says the before
  side is the one diffs use. There is no `--before` for `jadpo test`;
  the pages don't offer one.
- **No test reached passes.** It prints `nothing to run  no test reaches
  what changed since <base>` and exits 0, as `--failed` with nothing to
  rerun does; its JSON is `{ selection: { affected }, reached: 0, tests:
  [] }`. A run that did run says `since <base>` in its footer, and
  `selection.affected` names the base.
- **A project new since the base** has nothing there to compare, so every
  test reaches the change and all run.
- **No base commit is a usage error.** Outside git, before the first
  commit, with no default branch, with no history shared with it, or for a
  project git ignores, it is `cli.test_arguments` (exit 2), its next step
  `jadpo test`; a base a shallow clone doesn't hold names `git fetch
  --unshallow`, as `jadpo check` does.
- **With `--watch`**, the first run is what the branch changed reaches;
  each save after is measured from the last run, as always.
