# Identity: design notes

## Questions

1. **How simple should declaring authentication be?** The author names the
   user record, the methods and the public routes; the language owns
   transports, token formats, claims and lookups. Rails, Phoenix, Django,
   Sanctum and Auth.js all converged on this split.
2. **Are the principal's fields built in?** Yes: `id` (typed `User.id` or
   `Service.id`), `subject` and `strength`. Anything else is read from the
   entity, which keeps credentials free of profile and permission data.
3. **Is the service variant optional?** Yes, as long as one variant is
   declared. With no `service`, `service_key` is an error and
   `current_principal` is a user.
4. **One revocation setting?** `revocation_delay: 5m` in `application { }`,
   left out for immediate. The strict choice is the default, as with
   authentication on routes.
5. **How does code read the caller?** `current_principal` in routes only,
   passed to actions as a typed parameter. Signatures then show which
   actions need a caller, tests pass one in, and schedules visibly have
   none. Policy (area 9) gets the caller from the runtime without code
   passing it.
6. **Declared or built-in failures for a disabled caller?** Built in:
   `user_disabled` and `service_disabled`, kind `not_permitted` (403), with
   no declaration.
7. **Who stores service keys?** The language, as Laravel Sanctum owns
   `personal_access_tokens`. It generates `Service.issue_key`,
   `Service.keys` and `Service.revoke_key`, so an application can build its
   own key screens; the application declares only `Service`.
8. **What does a route say about authentication?**
   `authentication: RouteAuthentication.none` or
   `authentication: RouteAuthentication.fresh`, the one word a reviewer
   must not miss on a public route. Each of area 7's APIs lists the methods
   it accepts, so an admin API can refuse service keys without per-route
   lines.
9. **Can Jadpo code start and end a session?** Yes: `sessions.start(user_id)`
   and `sessions.end()`, callable only from actions run by a route, with the
   compiler setting and clearing the cookie and CSRF token. Passwords stay
   out. `sign_in:` checks the person for magic links, passkeys and
   providers (question 11); `sessions.start` is for a person the app checks
   some other way.
10. **How do tests, fixtures and seeds name a caller?** With
    `Principal.user(user)`, which only tests, fixtures and seeds write, and
    `as:` to sign a request in.
11. **Is "Sign in with Google" built in?** Yes. `sign_in:` in
    `authentication.jadpo` lists every way to check a person: magic links,
    passkeys and providers, each provider a connection in `app.jadpo`
    (area 11). For a provider the runtime generates
    `/auth/{provider}/start` and `/auth/{provider}/callback`, runs the
    authorization-code flow with PKCE, state and nonce, keeps each linked
    provider account in a compiler-owned table and starts a session.
    `on_first_sign_in:` on `authentication { }` is the one decision point
    for every way in, external tokens included: create a user, link an
    existing one, or refuse, with a refusal that looks the same to the
    person. Linking by email happens only when the address is verified.
    Tokens another service has already issued (Auth0, Clerk) are the
    separate `external_token` method. See "Checking the person: `sign_in:`"
    above.
12. **Should authentication checks read a cache?** No: authentication always
    reads the database (area 5). The strict default is one primary-key read
    of the session joined to the user's record; with `revocation_delay` set
    there is no read at all, which is faster than any cache. A cached
    session would survive a revocation made while the cache was
    unreachable, turning a cache outage into a security gap.
    `revocation_delay` is the one speed setting.
13. **How does an application act as an OAuth provider?** Built in, with no
    third-party authorization server, following OAuth 2.1 and OpenID
    Connect, as Doorkeeper (Rails), Passport (Laravel) and
    django-oauth-toolkit add it to a framework. An
    `oauth_provider: { scopes: { ... } }` block in `authentication.jadpo`
    declares the scopes, each with a description shown to the person. The
    runtime generates the authorization, token, revocation and discovery
    endpoints and the signing keys' public set: only the authorization-code
    flow with PKCE, refresh tokens that rotate, and client credentials for
    server-to-server clients; no implicit or password grants. Registered
    client applications are stored by the language, with generated
    `OAuthClient.register`, `OAuthClient.list` and `OAuthClient.revoke`, as
    service keys are. The consent screen is a route the application writes,
    because it is branded UI; it calls a generated `oauth.approve(...)`. A
    token arrives through `AuthenticationMethod.oauth_token`. Scopes from
    any token, `oauth_token` or `external_token`, narrow what policy allows
    (area 9): a grant can require a scope, and a token never allows more
    than the person could do themselves. Its uses are AI connectors (the
    MCP specification requires OAuth 2.1 for remote servers), integrations
    and marketplaces, and partners acting for a customer. Not built yet.
14. **How does the app act at another service for each user?** With an
    `OAuthGrant` credential on a connection, owned by one of the app's
    records; generated `start`, `callback` and `disconnect` routes, the
    start route needing a signed-in caller and keeping the `state` on the
    server against its session or API token; connecting needs the `update`
    grant on the owner; grants in `jadpo_grants`, encrypted with
    `grants: { encryption_key: }`; tokens held and refreshed by the
    runtime, never readable by code; every call names its owner with
    `on_behalf_of:`. See "Acting for a user at another service: OAuth
    grants" above and area 11.
15. **What switches the generated magic-link routes off?**
    `generate_routes: false`. `routes` is a reserved word, so
    `routes: false` can't be written; letting reserved words be member keys
    would loosen a rule every block relies on for its error messages.

## Decisions

| Topic | Decision |
|---|---|
| One passkey implementation | Every host runs the same ceremonies, the runtime's own in pure Rust on jadpo-value's ES256 and RSA checks (signature, challenge, origin, counter), held to `webauthn-rs` 0.5.5's answers by tests in which it is a dev-dependency, so no deployable links OpenSSL and `passkey:` and its magic-link recovery work alike on both targets |
| External tokens in tests and dev | Tests and `jadpo dev` replace the configured issuer with a local one keyed for the run; `as:` in a route test sends its token for the user's subject, and `jadpo dev token <user-id>` prints one. A deployable never accepts it. Keys whose `key_ops` leaves out `verify` are skipped like encryption keys; secret members still refuse the whole set. Found by an outside agent's library app, which needed a Python HTTP suite and a Rust host to test external-token staff sign-in (Richard, 2026-10-30) |
| Passkey attestation | Registration asks for no attestation, and a device's statement must be `none` or packed self-attestation, whose signature by the new key is checked; one signed by a certificate (packed with `x5c`, TPM, Android key, Apple, FIDO U2F) is `passkey_rejected` rather than taken unchecked, since the runtime reads no certificate chains and browsers send `none` when none is asked for. No attestation is kept. Every other check is `webauthn-rs`'s |
| Unnamed singletons | Carried from area 1: `application { }` and `principal { }` carry no name; the application's principal setting is removed |
| Root files | Carried from area 1: `app.jadpo` holds the application and principal; `authentication.jadpo` holds the methods |
| Colon rule | Carried from area 3: every member is `name: value`, so `user: { }`, `browser_session: { }` |
| Setting options | Carried from area 2: closed options are written `Type.value`, never strings (area 2, question 17) |
| Runtime kinds | Carried from area 4: `unauthenticated` and `misconfigured` are raised only by the runtime; authentication failures are never listed in `fails` |
| Principal in failures | Carried from area 4: the signed-in principal cannot be put in a failure's fields |
| Declarations | `application`, `principal` and `authentication` are each declared once (`semantic.multiple_*`), in any file of a single-file project and in `app.jadpo` and `authentication.jadpo` otherwise. A variant holds `subject:`, a required `unique: true` field of an entity kept in a PostgreSQL store, and an optional `active:`; left out, every record of the entity is active. `active:` is a condition on that entity's own fields named as a query names them (`Member.status == MemberStatus.active`): comparisons with literals, enum values, `none` and `clock.now`, joined with `and` and `or`. A record the entity's lifecycle hides can't sign in. `oidc:` is refused with its rename to `external_token:` |
| Browser sessions | `browser_session:` requires `cookie:` (1 to 64 letters, digits, `_` and `-`, starting with a letter). The token is 32 random bytes in hexadecimal in that cookie (`HttpOnly; Secure; SameSite=Strict; Path=/`), the CSRF token the same in `<cookie>_csrf`, readable by the application's scripts; both are kept only as BLAKE3 verifiers. A session lasts 30 days from its start, with no sliding renewal. Every method but `GET` that comes with the cookie needs an `Origin` whose host is the request's `Host` (when `origin:` is left out; see "Signing and origin settings") and `X-Jadpo-CSRF` matching the session, else 403 `csrf_rejected`. An unknown or ended session is 401 `invalid_credentials` and its response clears both cookies. A cookie is read only on an API that accepts `browser_session`; an `Authorization` header where no bearer method is built is 401 `invalid_credentials` |
| Where sessions live | `jadpo_sessions` is a system table in the store the principal's user entity lives in, in its migration snapshots, read with the user's record in one statement (question 12); area 5's `sessions:` store setting isn't needed while that holds, and a store of their own (Redis) would bring it back |
| Signing in on a request | Authentication runs after routing, inside the route's deadline and before its input is read; a route that selects `current_principal.user` refuses a service with 403 `not_permitted`. A signed-in caller's requests count against its own allowance, 600 a minute (area 16), counted per worker thread natively until the Redis store; a request with a credential that is refused counts against its address, and every other against its address as before. Idempotency keys are kept per caller (`user <id>`), and per `anonymous` on routes anyone may call. A response whose action started or ended a session isn't kept for a repeat, so a retry signs in again |
| Starting and ending sessions | `sessions.start(user_id)` takes the user entity's `id`, `sessions.end()` nothing; only actions call them, not functions, queries, tests, fixtures or seeds. Each writes the sessions' store, so the action writes that store (one store per action, area 6). A test that calls such an action keeps the session with no response to set it on. `sessions.end()` on a request with no session ends none and still clears the cookies |
| The caller in code | `current_principal` alone is a `Principal`, whose fields aren't read until a kind is selected; a route passes `current_principal`, `current_principal.user` or one of its fields, never both kinds. A caller's `id` counts as a record loaded earlier, so writing a record that refers to it needs no not-found failure. `as:` signs in a user through a real browser session (a session kept in its own transaction, the cookie, the CSRF token and an `Origin`); `as:` on a route anyone may call is `semantic.request_invalid` |
| Reports | Each API's OpenAPI document lists the accepted methods as security schemes (`browser_session` as an `apiKey` cookie) and requires them at the top; a route anyone may call says `security: []`, and every other answers 401 (`authentication_required`, `invalid_credentials`, `ambiguous_credentials`), 403 (`user_disabled`, and `csrf_rejected` on a write) and 503 (`authentication_unavailable`). The API record writes `authentication: none` under a route anyone may call. `jadpo routes` shows `required`, `none` or `fresh`. Wrong route and API values are `route.authentication_invalid` and `api.authentication_invalid` (area 7) |
| External tokens: network and provisioned subjects | Public HTTPS issuer and keys only, no redirects; exact issuer metadata may name a cross-authority public HTTPS `jwks_uri`, never token header URLs. EdDSA/RS256/ES256 verification uses area 19, followed by a current active-user lookup on every request. Compiler-owned bounded discovery/cache/refresh; no provider profile authority. Unknown subject is 403 `sign_in_refused` unless `on_first_sign_in:` takes it on. Scopes are not built yet. |
| Bearer credentials | `api_token:` and `service_key:` take only `signing_key:` (a literal is `semantic.auth_setting_invalid`), so each is written `{}`; `api_token:` needs the principal's `user:` and `service_key:` its `service:` (`semantic.auth_principal_required`). Each travels as `Authorization: Bearer <value>`, the scheme in any case: an API token is `jadpo_token_` and 64 hexadecimal digits, a service key `jadpo_key_` and 64, 32 random bytes kept only as their BLAKE3 verifiers. The prefix says which method a credential is; one the route's API doesn't accept, or any other value, is 401 `invalid_credentials` without clearing cookies. A bearer credential needs no `Origin` or CSRF token |
| API tokens | A token is a session without a cookie: a `jadpo_sessions` row with no CSRF verifier, lasting 30 days from `sessions.issue_token(user_id) -> ApiToken`, with no sliding renewal; a cookie never signs in with a token's row, nor a bearer with a session's. `sessions.end()` ends the token or session a request came with, needing either method. `sessions.tokens(user_id) -> List<IssuedToken>` lists the user's tokens that haven't ended, oldest first; `sessions.revoke_token(token_id)` takes a `Uuid` and deletes only a token, never a browser session; an unknown `id` revokes nothing |
| Service keys | `issue_key`, `keys` and `revoke_key` belong to the entity the principal's `service:` names, once `service_key:` is declared; on any other entity they are `semantic.unknown_callee`. `issue_key(service_id, expires_at: Instant) -> ServiceKey` keeps the key until `expires_at`, `keys(service_id) -> List<IssuedKey>` lists those that haven't expired, oldest first, and `revoke_key(key_id: Uuid)` deletes one. Keys live in `jadpo_service_keys` (`id`, `principal_id`, `verifier`, `started_at`, `ends_at`) in the service entity's store, read with the service's record, `active:` and lifecycle in one statement. A service caller's rate limit and idempotency keys are its own (`service <id>`) |
| Issued credentials in code | `ApiToken` and `ServiceKey` are built-in text types an `Output` can send; an entity field of either is `type.auth_credential_stored`. A response from an action that issued one is never kept for an idempotent repeat, so a retry runs again. `IssuedToken` and `IssuedKey` are built-in values with `id: Uuid`, `started_at: Instant` and `ends_at: Instant` that code reads. None of the six operations fails: like `sessions.start`, each takes an `id` the action has already loaded, and an action calls them (`type.auth_sessions_context`), writing or reading the store their table lives in; the two reads are also run by a `GET` route |
| Signing in from a route test | `as: Principal.user(...)` signs in through a browser session when the route's API accepts one, otherwise through an API token; `as: Principal.service(...)` through a key issued as `issue_key` issues one, lasting 30 days. Each is kept for real in its own transaction and sent as a client sends it. With nothing declared that signs that kind of caller in, `as:` is `semantic.request_invalid` |
| Listing from a `GET` route | `run: sessions.tokens(...)` and `run: <Service>.keys(...)` are the only generated calls a route runs, each on a `GET` and passing one argument, the holder's `id` (a placeholder, `input`'s field or `current_principal.user.id`); the call is `List<IssuedToken>` or `List<IssuedKey>`, so `output:` is exactly that. On another method it is `route.run_kind`, and `issue_token`, `revoke_token`, `issue_key` and `revoke_key` are `route.run_invalid`; with the method undeclared it is `type.auth_sessions_context`, as in an action |
| `IssuedToken` and `IssuedKey` in an `Output` | An `Output` field, and a route's `output:` as a `List`, may be either; on the wire each is an object of `id` (a UUID), `started_at` and `ends_at` (timestamps), never the credential. The API record gives each an `output IssuedToken` section and OpenAPI a schema of its own. They are made only by listing, so an entity can't store one (as any structured stored field, `toolchain.not_built_yet`) |
| Policy on a listing route | A route that lists reaches a `read` of the holder's entity, the same grant `sessions.tokens` needs in an action: no one granted is `policy.effect_ungranted`, and a route anyone may call needs `Access.public` (`policy.public_grant_missing`). The runtime runs it as a one-statement read at repeatable read with the statement the plan limited by those grants, so it lists the tokens or keys of holders the caller may read, and a list for any other holder is `[]` with 200, never a failure. There is nothing to prove for the output: its three fields belong to the credential, whose holder's `read` already decided the list |
| A caller held deep in a type | An `Input`, `Output` or failure field whose type holds a caller anywhere (in a `List`, `Set`, `Map` or option, or in a field of an object or a variant's data, followed through every named type it uses) is `type.auth_principal_input`, `type.auth_principal_output` or `type.auth_principal_failure_context`, as if it held the caller itself; an `Input`, `Output` or failure it uses is checked at its own declaration |
| Counting and undoing on a request | A route anyone may call runs as no one, so a request to it with a credential counts against its address before it runs, as every other such request does; only a route that needs a caller counts after signing in. An action whose failure its caller handles forgets what it did to the request's session with its writes: a `sessions.start` sets no cookie and a `sessions.end` clears none, and a token or key it issued doesn't stop the response being kept. Each API's record names the methods it accepts and each route the kind of caller it selects (area 7) |
| Signing and origin settings | `signing_key:` reads a `SigningKey` setting and `origin:` a `Url` setting, each written `config.<name>`; a literal, any other expression or a setting of another type is `semantic.auth_setting_invalid`, and a name no setting has is reported where it is read (area 10). With `revocation_delay:`, every built method (`browser_session:`, `api_token:`, `service_key:`) needs its `signing_key:` (`semantic.auth_setting_required`); without one a `signing_key:` is accepted and signs nothing, so the delay is switched off in one line. `origin:` is optional: given, a cookie write's `Origin` must be its scheme, host and port exactly (in lower case, without a default port or a path), so `Host` is never consulted; left out, the write's `Origin` must name the server its `Host` gives. A route test sends the configured origin |
| Signed parts | A signed part is `<payload>.<tag>` in base64url without padding: the payload JSON of the credential's method, its row `id`, its verifier, the caller's `id` and subject, when it expires and a browser session's CSRF verifier; the tag BLAKE3 in keyed mode under a key derived (BLAKE3 `derive_key`) from the setting's text, compared in constant time, in `jadpo_runtime`, host-agnostic and built for wasm32. It is signed with the current value and opens with the current or the `_PREVIOUS` one. It is made only after a read of the record, never by `sessions.start` or `sessions.issue_token`, so a credential signs in its first time by reading the record, as it would with no delay, and a caller disabled before signing in is refused at once. It expires the delay after that read, or when the session or the key ends if that is sooner. A secret beside a part that holds another verifier, a part no key opens, one for another method or one that has expired is never refused for that: the request reads the record by its secret |
| Renewing | A browser session's cookie and an API token are the 64 hexadecimal digits they are issued as, and after renewal those digits, `.` and the signed part; either form signs in with or without a delay, so turning one on or off signs no one out. A request whose credential has no good part reads the record (one statement, area 8, question 12) and its response renews it: the session's cookie set again, `HttpOnly; Secure; SameSite=Strict`, with `Max-Age` the session's time left, or the API token in an `X-Jadpo-Token` response header, which a client keeps; a client that ignores it reads the record on every request after the delay. A response whose action started or ended the session renews nothing, and neither does a refusal or a repeat answered from an `Idempotency-Key`. A `fresh` route reads the record by the credential's verifier whatever its part says, and renews it only when its part wasn't good. A write with a good part checks the CSRF token against the verifier the part holds |
| The key exchange | The runtime answers `POST /auth/exchange` when `revocation_delay:` is set and `service_key:` is declared with the principal's `service:`; it signs in to every API that accepts service keys and is listed in each one's record (`generated: exchange`, `output: ExchangedToken`), OpenAPI (`x-jadpo-generated: true`) and `jadpo routes` (`generated exchange`). It takes a service key directly and nothing else: an exchanged token is 401 `invalid_credentials`, a user's credential 403 (`not_permitted`, or `csrf_rejected` for a cookie without its CSRF token), a query string or body 422 `invalid_input`; it reads no `Idempotency-Key` and keeps nothing, so a repeat is a new exchange. It answers 200 with `token`, `jadpo_service_token_` and a signed part, and `expires_at`, the delay from now or the key's end if sooner, with `Cache-Control: no-store`. An exchanged token signs in wherever the API accepts service keys, without a read except on a `fresh` route, which reads the key with the service's record by the key's verifier the part holds; it is never renewed. A route the application writes at `POST /auth/exchange` is `route.path_overlap` |
| `sign_in:` and passkeys | `sign_in:` is a block in `authentication { }` holding `magic_link:`, `passkey:` and `providers:`, each once (`semantic.auth_method_duplicate`); anything else is `semantic.auth_method_unknown`. `passkey:` takes `expires_after:` (`1m` to `10m`, default `5m`; outside it, or not a duration, `semantic.auth_setting_invalid`, a hard limit rather than an acceptance, since a longer challenge buys nothing) and `path:` (`/` and lower-case segments of letters, digits, `-` and `_`, default `/auth/passkey`). It needs `browser_session:` with `origin:`, and `magic_link:` beside it (`semantic.auth_setting_required`). There is no `generate_routes: false` and no generated operation: the bodies are WebAuthn's, so an app's own route would add nothing. A person has at most 20 passkeys; a passkey signs in a browser session only |
| Passkey ceremonies | `webauthn-rs` 0.5.5's passkey ceremonies, its options member for member and its checks: user verification required, attestation `none`, ES256 and RS256, `credProtect` asked for as `webauthn-rs` asks. The relying-party ID is the configured origin's host and only that origin is accepted (no subdomain, no other port). Registration asks for a resident key (`residentKey: "required"`, `requireResidentKey: true`) and sign-in is discoverable (`webauthn-rs`'s `conditional-ui`, `mediation: "conditional"`), so no address is asked for and nothing tells which addresses have an account; `allowCredentials` is empty and `excludeCredentials` lists the person's passkeys. The user handle is 16 random bytes per passkey, never the user's `id`, and an answer's must match the passkey's. Its challenge is 32 bytes from the host's generator (the operating system's natively, Web Crypto's on Workers); the cookie and the user handle are the runtime's random bytes. Its state, the challenge and the passkeys excluded, is kept server-side only, and a stored passkey is read from its parts |
| Passkey challenges | `jadpo_passkey_challenges` keeps each by the BLAKE3 digest of its bytes, with its purpose, its binding, its state and when it expires, in the user entity's store. A sign-in challenge is bound to `<cookie>_passkey` (32 random bytes, kept as its digest; `HttpOnly; Secure; SameSite=Strict; Path=/`, `Max-Age` `expires_after:`, cleared on success), a registration challenge to the session row the request came with and its user; one per binding and purpose, a new request replacing it. The answer's challenge is taken with `DELETE … RETURNING` before the answer is checked, so it is used once whatever the answer; one missing, expired, bound elsewhere or for another user is `passkey_challenge_expired` (401). Expired challenges are swept when a new one is kept. The options routes take no body or query string, and every passkey POST needs an `Origin` naming the configured origin (`csrf_rejected`); the signed-in ones also need the session's CSRF token. Registering reads the record now (`fresh`) |
| Checking an answer and the counter | Any check that fails, an unreadable answer, an unknown or removed passkey or a user handle that doesn't match is `passkey_rejected` (401), never saying which. The counter is WebAuthn's strict check, as `webauthn-rs` makes it: when the stored or the answered count is above zero, one not above the stored count is refused and nothing is written; a passkey that keeps no counter sends `0` and passes. Backup eligibility may not change on a discoverable sign-in. On success the passkey's counter, backup flags and `last_used_at` are written only if its counter is still the one read (`passkey_rejected` otherwise), in the transaction that keeps the new session, which `user_disabled` (403) stops when the user's `active:` doesn't hold |
| Keeping and showing passkeys | `jadpo_passkeys` holds `id`, `principal_id`, `credential_id` (`bytea`, unique), `user_handle`, `credential` (the `WebAuthnCredential` JSON: bytes in Base64, the count as text, `last_used_at` left out until used) and `registered_at`. A passkey registered already is `passkey_already_registered` (409), a 21st `passkey_limit_reached` (409). `name` is required, one line (area 19's `Line`, 1 to 200 characters; else 422 `invalid_input`). Listing, renaming and removing reach only the signed-in person's passkeys, oldest first, any other `id` `passkey_not_found` (404); `PasskeyView` is `id`, `name`, `registered_at` and `last_used_at` (or `null`). The routes go in the first API that accepts browser sessions, its record (`generated: passkey`), OpenAPI (`x-jadpo-generated: true`) and `jadpo routes` (`generated passkey …`), and their failures' wording is Jadpo's own, on with `passkey:` (area 16) |
| Encodings of signed parts and passkeys | A signed part's payload records the encoding it was written in as `enc` (area 19, "Changing a standard type's encoding"); a part with none is read in the first encoding, and one of an encoding this release doesn't know opens nothing, so the request reads the record and is renewed, as with an expired part. A passkey is kept as `WebAuthnCredential`'s contract JSON, written and read by the codec the plan numbers in its JSON table, which holds it to the type's rules, with the encoding in `jadpo_passkeys.encoding`; one with none is read as it was kept (its count a number or its digits) and written in this release's encoding the next time it signs in. A passkey of an encoding this release doesn't know is `passkey_rejected` and isn't listed |
| Magic links | `magic_link:` takes `address:`, `link:` (required: a path on the app's site, one `/`, no query, fragment or `\`), `expires_after:` (`1m` to `1h`), `code_attempts:` (1 to 10), `codes_per_hour:` (from 1), `failed_codes_per_day:` (1 to 50), `resend_after:` (above zero), `same_browser:` and `path:`; past a limit is `toolchain.not_built_yet` until acceptances. It needs the browser session with its `origin:`, the `email:` connection unless it names `send:`, and `display_name:`. Its routes go in the first API that accepts browser sessions, beside the passkeys'; the redemption only with `api_token:` |
| What is kept | `jadpo_sign_in_requests` holds one row per address, keyed by the BLAKE3 digest of the address in lower case, so the send and wrong-code limits count every way of writing it as one, with the digest of the address as written beside it; a code is confirmed only with that exact address. The link's 32 bytes and the six digits (each drawn evenly) are made as the email is sent, not when it is asked for, and kept only as verifiers: the token's BLAKE3 digest, the code's keyed by its request; the address is sealed under the token (a BLAKE3 key stream), so a confirmed link can name it. The outbox keeps only the address, the locale and the request's id, so neither it nor the table ever holds a link or a code; a delivery whose request was used, replaced or has expired sends nothing. Rows are swept once nothing in them counts |
| Asking and confirming | `POST /auth/magic-link` needs no `Origin`, so the app's own client asks too; its `locale` is a supported locale's name or BCP 47 tag, else `Accept-Language` decides; a `return_to` that isn't a site path is 422 `invalid_input`. An email goes to an address an account has (active or not; confirming then answers `user_disabled`) or, with `on_first_sign_in:`, to any. The confirm needs an `Origin` naming the browser session's origin; the redemption, for the app's own client, needs none. The person is found by the address exactly as the user's field holds it. A link opened in another browser under `same_browser:` is refused and left unused; the binding cookie is `<cookie>_sign_in` and is cleared once signed in. Wrong guesses count against the code and the address's UTC day only where the address has a row; past the day's, even the right code is `sign_in_codes_disabled`, with `Retry-After` until midnight UTC |
| Sign-in providers (Richard, 2026-10-30) | Each provider is a `Driver.oidc` connection with `issuer:` (`Url`), `client_id:` (`Text`) and `credential:` (a secret), named in `sign_in: { providers: [...] }`; `SignInMethod` gains a value per provider, after `external_token`, in the order `providers:` lists them. The routes mirror the OAuth-grant routes: `POST /auth/<name>/start` (no caller; `Origin` the browser session's; `{ return_to? }` a site path, else `sign_in_return_invalid`) answers `{ address }` and sets `<cookie>_provider` (32 random bytes, `HttpOnly; Secure; SameSite=Lax; Path=/`, ten minutes); `GET /auth/<name>/callback` takes the request once by its `state`'s digest, checks the binding cookie, exchanges the code with PKCE `S256` and the client secret (`client_secret_post`), checks the ID token (provider keys under area 8's fetch limits, exact `iss`, `aud` naming `client_id`, `azp` when several audiences, `exp`, `nonce`), and starts a browser session, answering `303` to `return_to`; a refusal answers `303` to `return_to?error=<code>`, with the new `sign_in_provider_failed` (401) for an expired, used or foreign `state`, a provider's error and an ID token that doesn't check. The PKCE verifier and the nonce are keyed BLAKE3 of the binding cookie and the `state`, so nothing secret is stored. Browser sessions only. A provider account finds its user only through `jadpo_sign_in_links`, never by `subject:` or an address, so `providers:` without `on_first_sign_in:` is `semantic.auth_setting_required`. Tests sign in with `test_providers.sign_in(method, TestAccount { subject, email, email_verified, name })`, which drives both routes against the local issuer standing in as the provider's authorization and token endpoints. `jadpo dev`'s local issuer shows an account-chooser page, designed with the design skills first. Microsoft is taken with a tenant's own issuer only: `common` and `organizations` publish a templated issuer, which the exact comparison refuses |
| First sign-in | `FirstSignIn` is a built-in object only the runtime makes (`method`, `address`, `address_verified`, `subject`, `name`); `SignInMethod` is a built-in enum of `magic_link`, `passkey` and `external_token`, a provider's value coming with providers. `on_first_sign_in:`'s action runs as the system (`Access.system` grants it), in its own transaction, before the session starts; a failure it declares is `sign_in_refused`, `unavailable` is `authentication_unavailable`, a fault `internal_fault`; the user it names is then read by its `id` and must be active. The reason a refusal had reaches the log and `SignInRefused` ("Sign-in events"). For an external token (chunk A7) the user is read by the subject field, else through `jadpo_sign_in_links` (way in and subject as the token sent it, to the user's `id`), in one statement; a miss takes a transaction-scoped advisory lock on the way in and subject and reads again, so the action runs once per subject and concurrent first requests sign in through its link. The link is kept, with `SignedIn` (`first_time: true`), for any user the action gave that the lifecycle shows, active or not |
| The app's own sign-in email and sending | `email:` and `send:` name a type or an action as `on_first_sign_in:` does, `<domain>.<name>`. `SignInCode` is a built-in type made of text (six digits); like an API token it is never kept in an entity (`type.auth_credential_stored`), nor put in an `Output`, a failure or an event (`type.secret_exposed`), nor written as JSON. `MagicLinkEmail` is a built-in object only an email copies from, with `pick:` or `include:` (`type.not_record` elsewhere); the email `email:` names may hold no field of its own and is never emitted (`event.emit_invalid`), so the outbox never holds its link or code. Its delivery is still Jadpo's: the link and the code are made as it is sent, the app's email filled from them and rendered as any of its emails is, in the request's locale. `send:` keeps `display_name:` required; its action is a subscriber's of `jadpo.MagicLinkEmail`, run as the system, reaching no tenant, retried and given up under area 12's defaults, each attempt given a link and a code of its own, so only the latest works; a request used or replaced since runs nothing |
| The app's own routes | `generate_routes:` is `true` or `false`, and `false` beside `path:` is refused (`semantic.auth_setting_invalid`). The operations need `magic_link:` with `generate_routes: false` (`semantic.auth_setting_required`), so each link is asked for and used one way; only an action calls them (`type.auth_sessions_context`), and a route's `run:` never does (`route.run_invalid`). Their arguments are positional: `request` takes all three, `none` for the path meaning `/`, and a `locale` the app doesn't support falls back to its default. They run the generated routes' own code. `request` keeps the request in the action's transaction and leaves Jadpo's email as the action's own event, so it goes once the action commits, and an action that fails sends nothing and counts no send; the sweep of rows nothing counts runs on its own. `redeem` and `redeem_code` use the link or the code in a transaction of their own, before the action's writes, as the routes do: a wrong code stays counted though the action fails, and a used link or code stays used if the action fails after, so the person asks again; `on_first_sign_in:`'s action runs in its own transaction while the app's waits. An action that has asked for a link can't use one (a fault: it would wait on its own row). `same_browser:`'s cookie is read from the request; the response of the route whose action asked sets it, and the response of one whose action used a link clears it; neither response is kept for an idempotent repeat. `SignInToken` is a built-in type made of text (64 lower-case hexadecimal digits), held only by an `Input` or an `Object`: never kept (`type.auth_credential_stored`), nor put in an `Output`, a failure, an event, an email, a message or a prompt (`type.secret_exposed`), nor written as JSON. `MagicLinkRedeemed` is a built-in object only the runtime makes: `user_id`, the user entity's `id`, and `return_to: Text`, `/` unless the person gave a path. Their failures are the routes' own, raised by the runtime and passing through the action: `rate_limited` and `sign_in_codes_disabled` with `Retry-After`, and `sign_in_return_invalid` (`invalid_value`, 422), worded under the `magic_link_routes` feature of Jadpo's text. The API record and OpenAPI list the app's routes as its own, and no generated ones |
| Sign-in events | `SignedIn`, `SignInRefused` and `SignInCodesDisabled` are built-in types only the runtime emits (`event.emit_invalid`), named in `on:` as an app's events are, and reserved as names; a subscriber of one needs `magic_link:` (`subscriber.event_invalid`), and its fields are area 8's, `user_id` typed as the user entity's `id`. A test, fixture or seed may build one, or a `FirstSignIn`, with every field, to call an action directly; elsewhere `type.not_record`. Each is kept in the outbox of the store sessions are kept in, under `jadpo.<Name>`, its payload the runtime's own (the user's `id`, the way in, the reason, `until` in milliseconds), and only when a subscriber listens, so nothing records who signed in that no one asked for. `SignedIn` commits with the session or token it reports; from the app's own routes it is the action's event, delivered only if that action commits. `SignInRefused` and `SignInCodesDisabled` are kept in a transaction of their own once the refusal is decided, so they stay though the action fails, and a store that can't keep them leaves the refusal unchanged. `user_id` is given when the link's or code's address has a user (looked up only when something listens) or the user is disabled; never for an expired link or a first sign-in the app refused. A first sign-in with no `on_first_sign_in:`, or whose action named no visible user, is `refused_by_app`; a fault or an unavailable store publishes nothing. `SignInCodesDisabled` is published by the wrong code that reaches `failed_codes_per_day:`, `until` the next midnight UTC. The reason, and for `refused_by_app` the failure the action declared, goes on the request's log line (`jadpo dev`: `└─ sign-in refused · refused_by_app · SignUpClosed`; `refused` in `--json`), never in the answer |
| Passkey recovery, events and route tests | `passkey:` with no `magic_link:` written in the same `sign_in:` is `semantic.auth_setting_required`, reported only once the browser session's origin is there, so a project missing both hears about the origin first. The device lists a passkey under the user's `magic_link:` `address:` field, read by the user's `id` as the request reads the record; a user without one is listed under the subject. A passkey's sign-in publishes `SignedIn` (`method: passkey`, `first_time: false`) committed with the session, and `SignInRefused` for `passkey_challenge_expired`, `passkey_rejected` and `user_disabled` in a transaction of its own, its reason on the request's log line; `user_id` is given when the answer named a registered passkey, never for an unreadable answer, a challenge that expired or a passkey removed or never registered. A malformed body, a missing `Origin` and an unavailable store publish nothing, as for magic links. `PasskeyAdded` and `PasskeyRemoved` carry `user_id` and `passkey_id` (the routes' `id`, never the credential ID), commit with the passkey they report, and need `passkey:` for a subscriber (`subscriber.event_invalid`); they are kept under `jadpo.<Name>` only when a subscriber listens, as the sign-in events are. `test_passkeys.register(user, name)` and `.sign_in(passkey)` are checked in tests only (`semantic.request_invalid` elsewhere, as `request` is; `semantic.auth_setting_required` with no `passkey:`), `name` any value built on `Text`; each `TestPasskey` is a software authenticator of its own (ES256, discoverable, verifying, no attestation) that only a test's host has, natively and in a test Worker under workerd (no deployable does), opaque to code. `register` signs in as `as:` does and sends the application's own `Origin`; `sign_in` starts from a browser with no cookies. A refusal on the way to a passkey ends the test as a fault naming the route and its code. A test calling only `test_passkeys` counts as the kind its other calls make it (an action test when a fixture makes its user), since the generated routes are not graph nodes |
| The system's sign-in actions and tenants | The magic-link `send:` action runs with its delivery's tenant, as a subscriber's does, which for `jadpo.MagicLinkEmail` is none, and `on_first_sign_in:`'s action with no tenant: each reaches only records every tenant shares, never every tenant's, as area 9 says of the system inside a request. Each is let in only by `Access.system`: what only `Access.public` lets it in to is `policy.system_grant_missing`, at its `send:` or `on_first_sign_in:` |
| Route tests through the magic-link routes | A route test calls the generated routes with `request { }`. Their inputs are built-in `Input` types named as the API record names them, `MagicLinkAsk`, `MagicLinkConfirmation` and `MagicLinkCode`, which only a test, a fixture or a seed builds, a field that may be `none` left out at will; the confirmation answers `MagicLinkConfirmed` and the redemption `MagicLinkToken`. A test's request carries the app's own `Origin`. `SentEmail` gives the sign-in email's token and code as `sign_in_token: SignInToken?` and `sign_in_code: SignInCode?`, so a test never parses them out of the text and the token stays typed |

## Moved from the area page

When [Identity](../08-identity.md) was rewritten to the
[writing guide](../../writing.md), its references to the questions above,
its comparisons with other frameworks and the reasons it gave moved here.
Nothing in this list changed a rule.

- **Where a credential travels** is decided by the method, from a fixed
  list (question 1).
- **The principal's fields are built in**: `id`, `subject` and
  `strength`; a role, tenant or email is read from the entity
  (question 2).
- **`service:` is optional**, since most applications only have users
  (question 3).
- **`revocation_delay:` is the only revocation setting**, and leaving it
  out gives the strict behaviour (question 4).
- **`current_principal` exists only in routes that need a caller**
  (question 5).
- **`user_disabled` and `service_disabled` are built in**, never declared
  (question 6).
- **Jadpo stores service keys**, with generated `issue_key`, `keys` and
  `revoke_key`; the application declares only `Service` (question 7).
- **A listing of tokens or keys goes through policy** like any query's
  (question 8, with area 9).
- **An action starts and ends a session** with `sessions.start` and
  `sessions.end`, and the compiler sets and clears the cookie and CSRF
  token (question 9). Rails (`start_new_session_for`,
  `terminate_session`) and Phoenix (`log_in_user`) generate the same two
  calls.
- **API tokens are issued by an action and shown once**, like Laravel
  Sanctum's `createToken`.
- **Sign-in providers** are connections in `app.jadpo` (question 11, and
  area 11's "No presets"), and `on_first_sign_in:` links an existing user
  by address only when the address is verified (question 11).
- **Acting as an OAuth provider** is separate from both signing in and
  OAuth grants (question 13).
- **Passkeys are the language's, as magic links are**, because the
  ceremonies are where hand-written sign-in goes wrong.
