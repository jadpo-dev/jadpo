# Personal data: design notes

Why [Personal data](../15-personal-data.md) is the way it is: the decisions behind it, how it fits the rest of the language and what it carried to other areas. An app author reads the area page, not this one.

## Consistency with the rest of the language

- **Hard delete.** Area 5 says code cannot hard-delete a record with a
  lifecycle. Erasure does, as purge does; both are the compiler's own
  operations, which area 9 exempts from policy.
- **Two shapes for an end date.** `retention:` reuses purge's `after:` and
  `since:` but applies to visible records too. Purge stays the form for
  soft-deleted records.
- **Grants for erasure and export.** Area 9's grants are create, read, update
  and delete; this page maps erase to delete and export to read rather than
  adding effects.
- **`subject` already means something.** Area 8's principal has a `subject`
  (the sign-in identifier), so this page uses "person", not "data subject",
  in source.
- **What an export reaches.** It is what `erase` reaches, read rather than
  written, so what the law gives one person can't drift from what the
  other deletes. The one exception is another person's own record that
  refers to them: erasing clears only the reference, and exporting it would
  hand one person another's data.
- **An export with nothing to say.** `User.export` doesn't fail: the page's
  example declares no `fails`, a history gives an empty page for a record
  the caller may not read, and a person's export gives one with nothing in
  it the same way, whether they are absent, erased or just not the caller's
  to read.
- **Reading more than one store.** `export` reads each store in a read-only
  transaction of its own, beside the action's, since it must reach records
  across every store where `erase` does and an action may write only one.
- **A `File` goes as its link, however deep.** The area's own rule is that
  whatever can't be carried out in full is refused where it is written; a
  link that goes nowhere would be a silently partial export. A `File` inside
  a structured value is a link too, written by its field's codec with each
  file it holds as a link, and an `ExportSummary` field is exported with
  its file, though a batch's other records stay out as they do from a
  response.
- **The after-`erase` test.** Generating one for each person entity needs
  a person to make, which data builders will give. Until then, every test
  that erases a person is held to its export holding nothing, checked after
  the test's deliveries.
- **Options as enum values.** `PersonalData.contact` and `Erasure.deleted`
  follow area 2's `Type.value` rule and its "values, not verbs" naming.

## Why the area page is the way it is

- **A fixed list of categories.** The fourteen `PersonalData.` categories
  follow GDPR's special categories and the common groups used by privacy
  tools such as Fides. A bare `personal: true` can't tell health data from
  an email address, and there are no custom categories, so reports stay
  comparable and the sensitive-data rules exact.
- **The marking is the classification.** Hashing every marked field in
  logs, whatever its type, refines area 4, which logs dates and numbers as
  values.
- **Ownership by references, not tags.** The compiler reads every
  reference to a person to find their records, because tagging each owning
  reference would repeat what references already say. Only a direct
  reference counts: following a chain would let a todo's owner hold on to
  what someone else wrote on it.
- **No crypto-shredding.** There are no per-person encryption keys:
  deleting a person's key breaks unique lookups, indexes and search on
  encrypted fields, and no regulator has said key deletion counts as
  erasure. Backups are handled by the erasure log instead.
- **Legal holds left to the app.** Holds and restriction while a complaint
  is open are rare in the apps Jadpo targets, and a built-in one would
  also have to pause purge and retention.
- **No purpose or consent in the language.** The compiler can check
  neither, so purposes and lawful bases belong in the privacy notice, and
  consent is ordinary application data.
- **Access records only for sensitive reads.** Reads of ordinary personal
  data aren't recorded one by one: GDPR asks for accountability and
  security, not a log of every read, and that would log almost every
  request.
- **No region setting.** One the compiler can't verify would give false
  comfort, so residency is by deployment, and the report names the setting
  that says where each store is.
- **Encrypted fields.** The full design of `encrypted: true` belongs to
  this area and is built with personal data, together with keys held as
  data (a key per device or person in an encrypted field, usable only as a
  `crypto` call's `key:`).

## Decisions

| Topic | Decision |
|---|---|
| Setting options | Carried from area 2: options are enum values written `Type.value`, values rather than verbs |
| References | Carried from area 5: every field typed `X.id` is a reference with a required `on_delete:` |
| Lifecycle | Carried from area 5: `purge: { after: since: }` deletes hidden records; code cannot hard-delete a record with a lifecycle |
| Caches | Carried from area 5: caches are opt-in copies for display reads; erasing personal data wipes cached copies immediately |
| Logs | Carried from area 4: identifiers, numbers, enums, booleans and times as values; text as a keyed hash; secrets never |
| Stores | Carried from area 5: an action writes at most one store; stores declared in `app.jadpo` |
| Marking | `personal: PersonalData.category` from a fixed list of 14, eight sensitive |
| The person | `person: true` on the entity, and only `true`; several person entities allowed |
| Belonging | A record belongs to the people it refers to directly, never through a chain: a reply on another user's todo belongs to its author alone. Erasure reaches further, through what it deletes (`data.personal_unreachable` asks whether it can), and a marked field past a record it keeps is out of reach. A kept record that refers to no person loses its marked fields when erasure deletes what it refers to (Richard, 2026-11-01) |
| Erasure outcomes | Generated `Person.erase(id)`; outcomes follow `on_delete:`; `erase: Erasure.deleted/.anonymised/.retained` required on restricted references |
| Kept records | Field-by-field erasure on the person too: retained fields stay until retention ends, the rest is cleared, the person cannot sign in; purge deletes the rest automatically. The record is hidden from every query, `get` and include by default, as a lifecycle hides one; a query opts in with an explicit setting, allowed only if it reads nothing but `id` and retained fields, and the report lists those queries (Richard, 2026-11-01) |
| Reading what is kept | `include_erased: true`, the query's own section, so a reader sees it where the query is written. It takes only `true`, like `person:`. Read means the result, the conditions and the order; policy's own conditions don't count, since they decide who asks, not what is learned. An include is refused, since it reads more than the person's kept fields |
| Backups | An erasure log replayed at every start, re-erasing anyone logged who is still present; no per-person keys. It lives in a store the app names in `privacy:` that is not a person's own database, or a store of files, so a database restore can't roll it back (Richard, 2026-11-01) |
| Records in another store | A reference to a person may cross stores when it says `erase:` and has no `on_delete:`. It isn't a foreign key: erasure's generated subscriber applies the outcome in that store after the main commit. `data.reference_across_stores` still refuses `on_delete:` across stores and a reference across stores to anything that isn't a person (Richard, 2026-11-01) |
| `PersonErased` | Carries the person entity's name, its `id` and when they were erased, nothing personal; providers' keys join it with erasure at providers (Richard, 2026-11-01) |
| Legal holds | Left to the application |
| Export | Generated `Person.export(id)` as JSON of everything belonging to the person, credentials left out |
| Retention | `retention: { after: since: }` on a field (clears) or entity (deletes); periods from config; applied by the purge schedule |
| Retention, as built (chunk P2) | `after:` is a `Duration` setting, never a duration written in place, since the page puts every period in `config.jadpo` (`data.retention_period`); `since:` an `Instant` field, a record whose `since:` is `none` not counted yet. A field's retention needs a nullable field no lifecycle owns or reads (`data.retention_field_required`, `data.retention_lifecycle_field`), since clearing a lifecycle's field would show a deleted record again; clearing is a change, so `Generated.on_change` fields take the run's time. An entity's deletes hidden and visible records with their cascades, and a record a `restricted` reference holds, directly or through a cascade, is a compile error (`data.retention_held`) rather than purge's quiet wait, so no record outlives its retention unseen. Someone who signs in is deleted with their sessions, keys, passkeys and sign-in links in one statement, reached through a cascade too, and a `File` a retention lets go of has its bytes deleted (chunk P4). One purge schedule per entity applies its retention, then its purge, then its fields' retentions, sharing 20 batches of 500 a run; `items` counts records deleted and values cleared. No application test runs it, as for purge |
| Erasure, as built (chunk P3) | A record's outcome comes from the reference linking it to a record erasure deletes: its `erase:`, which may be written on any reference into records erasure deletes and overrides `on_delete:`, or else cascade as deleted and cleared as anonymised. Erasure walks on only through what it deletes; a kept record's own children stay with it, as when an ordinary delete clears a reference. `erase:` is required on a `restricted` reference into records erasure deletes (`data.erase_required`), not on one into records it only keeps, where it would never be read; a field it clears must be nullable (`data.erase_field_required`), `Erasure.retained` needs the entity's `retention:` (`data.erase_retention_required`), and an `erase:` on a field that is no reference, on a reference to records erasure never deletes, or on an event's field is refused (`data.erase_unreached`). `User.erase` takes the person's `id`, no block and no `conflict:`, needs `delete` on the person's record, reaches them hidden or not, and fails with their not-found failure; an action calling it runs at repeatable read, so a record added since its snapshot reruns or fails it rather than being cleared unseen. One statement does it all, the sign-in state of each deleted entity someone signs in as included |
| Erasure and retention, as built (chunk P4) | A kept record whose own references hold more than one person, or another person beside the reference erasure clears, is asked at erasure whether each still holds one erasure keeps; its marked fields are cleared only when none does, in the same statement, so the check sees the snapshot erasure works from. A record with one such reference, which is the one cleared, is cleared as before, and another person's own record loses only the reference. A `File`'s bytes, deleted or cleared by erasure or retention, go through area 16's count of holders (chunk B3), so neither needs code of its own: erasure's commit releases them, and the tick's sweep those a purge releases. A retention cascading to someone who signs in deletes their sign-in state in its statement, found by following the cascades from the records deleted |
| The person's own record, as built (chunk P4b) | A person's own field means one that isn't a reference: on a reference `erase:` keeps what it means on any reference, so its own record stays field by field only when such a field says `Erasure.retained`. Anything else there says nothing the record doesn't already do, so `Erasure.deleted`, `Erasure.anonymised` and `Erasure.retained` on an unmarked field are refused (`data.erase_own_field`). The time goes in a column of its own, `jadpo_erased_at`, added by a migration like any column, kept the first time. An entity that stops keeping records retires the column like any field, with a person's decision, and the migration fails while a record holds a value, since it would show those records again as ordinary ones. The fields that stay and the unmarked ones keep their values; the statement that deleted the record updates it instead, so everything else about erasure is the same. The hiding sits in the one place every statement gets a lifecycle's `visible:`, and it reaches parents too, unlike `visible:`, and every sign-in lookup, so there is nothing else to hide. As with a record a lifecycle hides, a record written later can still refer to them, since the row is there. A subject must have a value, so one that is marked stays or isn't marked, which the compiler says rather than choosing. A retired column on a record whose marked fields erasure clears goes with them, unmarked or not, since the marking left with the field; so the statement names it until it is dropped, and an erasure on a server still holding that build fails, all or nothing, once the column has gone. A retired entity's records are out of erasure's reach, as area 5 says, which is why retiring one needs an acceptance. A reference on such a person that would delete them when erasure deletes another entity's records is refused (`data.erase_own_field`), since the law keeping their record doesn't depend on who was erased; their references to records erasure deletes are cleared, as on any record it keeps, and one to their own entity reaches only someone else kept the same way |
| Other stores, `PersonErased` and the log, as built (chunk P4c) | One statement a store, each a walk from the person's `id` that stays in it, so a reference to a person crosses stores and nothing else does. The person's own runs in their transaction; each other is the generated subscriber `erasure in <store>`, safe to repeat since it finds nothing a second time, so it keeps no handled record. A person the walk deletes is erased in their own right, with their own `PersonErased` and entry, so a chain across three stores needs nothing else. Those subscribers and `erasure log` are tried for a month, then `failed` for an operator. The log keeps the person entity's born name, so a rename finds its entries. In a store of files each person is a file under `erasure-log/<born>/<id>`, which no file's key can name, and a new `list` of the capability's finds them. The replay reads a thousand entries at a time, asks each store which it holds anything of (a person not yet erased, or a reference to them), and runs the same statement for those, with the time logged, so a repeat changes no times; what it emits waits for the sweep. A replay that can't finish keeps the app from serving (the page says it is erased before the app serves anything), on a Worker at each isolate's first request. Nothing reads through such a reference, since a statement reads one database: an include and a membership's `member:` are refused, and a tenant's check of a reference skips it. *Rejected:* a high-water mark in each store, so a start replays only what is new, which a partial restore could leave wrong; a sweep comparing stores, which no database can do. **Decided 2026-11-11, Richard accepting the recommendation made in chunk P4c, since the decided pages don't say:** an app that calls `erase` must name a log (`data.erasure_log_required`), because the page makes it the app's to name and an erasure a restore could undo is the weaker choice; a person another store refers to goes only by erasure (`data.person_removal_across_stores`), because a delete, a purge or a retention would strand those records beyond any erasure, and applying `erase:` from them would be a choice of its own; a month of attempts before a delivery is `failed`, the time a person's request has by law; and `PersonErased`'s field names, `entity`, `id` and `erased_at`, and the log event `runtime.erasures_replayed` |
| Data requests, as built (chunk P11) | **Decided 2026-11-11, Richard accepting the recommendation, since the page doesn't say:** `privacy:` turns the routes on once it says anything beside `erasure_log:`, so an app naming only where its erasure log lives grows no routes; the signed-in routes have no switch of their own. Switching them off is `generate_routes: false`, as for every generated route; the page's `routes: false` can't be written, `routes` being a keyword. A person is found by `magic_link:`'s `address:` or else the user's `subject:`, active or not, since someone disabled can still ask for their data; a user who isn't a `person: true`, or isn't findable by an `Email`, is `data.privacy_person_required`. **The address check goes only to an address with an account**, as a magic link's does: the answer is `202` either way, so nothing reveals who has one, and nobody else is mailed a link they can't use. Its link is a `SignInToken`, the same 64 hex digits as a sign-in link's, rather than a new type. The routes answer `202` with `request_id`, `kind` and `deadline`, an erasure's cancel `204`; `privacy_link_expired` (401) for a used or expired link and `privacy_person_not_found` (404) for staff naming no one. `privacy.create_request(user_id, kind, identity_check)` takes a role held across the application and nothing wider, since anyone it lets in may start an erasure of anyone's data. Asking again while a request of that kind is open gives the same request, so two erasures can never run with one cancelled. The cooling-off is 14 days, the page's default, with no setting yet. **The cancel link is in `PrivacyErasureScheduled` and so in the outbox until delivered**, as the page puts the download link in `PrivacyExportReady`: an address can't be read back from it. A cancellation emits no event, the page listing five, only its access record. The address-check limits are one send a minute and five an hour per address, counted alike for every address; the routes otherwise keep the default limits, which on Workers are the counts the binding already has. A deadline is the same date next month in UTC, a day the next month lacks being its last. Left for the exports chunk: the address check's `email:` and `send:`, built with the other three |
| Exports, erasures and their emails, as built | **Decided 2026-11-11, Richard accepting the recommendation, since the pages don't say:** each piece of work is a *step*, one outbox row with a delivery to the generated subscriber `privacy requests`, due when the step is, written with the request in its transaction, so it commits with it, is retried, shown and given up as any delivery is, and needs no schedule of its own; a repeat finds its request has moved on and does nothing. **A link opens a frontend page**, as the other two do, `exports: { link: }`, `/privacy/download` unless it says, and that page posts `POST <path>/exports/download`, because a `GET` would be spent by a mail scanner and the file would then be gone. **`exports:` is required** once `privacy:` takes requests, naming a store of files, since no default says where a person's data goes; `keep:` runs `1d` to `30d`. **`privacy.download(token)`** is a fourth operation beside the page's three, giving a `PersonalDataExport`, because `generate_routes: false` would otherwise leave no way to reach the file. **The file is encrypted under a key derived from the link's token**, which is kept only as its digest, so neither the store nor the database opens it; an export file is the one thing the runtime keeps whose bytes it can't read without the link. It is deleted when the link is used, and at the link's end in case that failed; an erasure deletes what is left. **`File`s in a data request's export last as long as the export's link**, not five minutes: the page says a link in an export has to be followed as soon as it is made, which a seven-day download can't do. **`erasures: { cooling_off: }`**, `1d` to `21d`, since the page says the app sets it and names nothing to set it with; 21 days leaves a week of the shortest legal month for the providers. **An application that takes requests must name an erasure log** (`data.erasure_log_required`), as one that writes `erase` must. **The completion email goes once every generated delivery of the person's `PersonErased` has succeeded**, the log's and each other store's as well as each provider's; one that gave up marks the request `stalled` and the step goes on retrying, so an operator's retry finishes it. **The address is copied into the outbox at the erasure**, as a provider's key is, moved to the completion's own row and gone once sent; only the completion email reads it, since no application subscriber is given it. **A wording is the entity's name in `lower_snake_case` in its domain's language files**, as an email's subject is. **`kept` lists a kind of record once**, with the last end of its retention, since a person with 300 fines needs one line. **The alert comes a week before the deadline** and `PrivacyRequestOverdue` when it passes; a date in an email is `date_long` in UTC. `privacy:` needs a browser session's origin whenever it is on, since every link opens a page at it; the address check's `email:` and `send:` work as magic links' do, a link and a token made for each attempt |
| Access records | Every export, erasure and read of a sensitive field recorded without values |
| Logs of marked fields | Every marked field hashed in logs, whatever its type (amends area 4) |
| Purpose and consent | Not in the language |
| Where personal data goes, as built (chunk V5) | `personal:` goes on an entity's, an event's or an email's field, and on an object, input or output a package declares, read by the name the tables know a package's type by, so its mark never lands on an entity of the same bare name; on an app's own object, input or output it is `type.unknown_setting`, since the value is followed back to its marked field. The report lists every connection a value goes out through: a provider's operation, a package's action, a file store, a model, an email and a webhook's reply. Stores and caches are chunk P8's, and the report says so. Where the compiler can't tell, it counts as reaching: what decided a value, everything a package's action is passed, a value by what its type marks, a whole parameter by everything its type holds, anything a library's function was given in any part of its result, and anything a provider was sent in any part of its answer. That last one counts only for the report, because holding a provider's id to the marks of the name it was made from would make every stored id personal data under `semantic.ai_field_unmarked`. `jadpo check` writes the report only for a project with no errors, and removes an older one otherwise, since a body with errors may hold calls nothing can see. A library's function result, and a local's read typed by the local, also count in area 21's check, which they had slipped past |
| Report and residency | `build/report/personal-data.md` and `.json`, shown in review when it changes; residency by deployment per region |
| Data requests | Endpoints only, no pages: `POST /privacy/requests`, `/confirm` and `/cancel` for self-service, the emails linking to the frontend's `link:` and `cancel_link:` paths; signed-in `POST /privacy/export` and `/privacy/erasure` for the person only; staff actions granted in policy; export by expiring link, erasure after a cooling-off period, events at every step; the emails are area 16's built-in emails, each taking `email:` or `send:` |
| Unreachable personal data | A marked field that belongs to no person is a compile error (`data.personal_unreachable`, reported once per entity at its first marked field); every reference into a person's records has an erasure outcome. Only `personal:` marks a field for this: a standard type that is personal data whatever holds it is treated as marked in logs, caches and access records (area 19), not here, so a business's own phone number doesn't make it a person |
| An email address is personal data (Richard, 2026-11-04; chunk A20) | A field typed `Email`, or built on it, counts as `PersonalData.contact` with no `personal:`, because the 0.2.0 run read a customer's address through a public route and nothing said so. It joins the standard types that are personal data whatever holds them, so logs, the report, a public cache, a model, an audit and a connection's acceptance all count it, with its name in the report beside a field of it. Two things follow that those types don't have, or have differently. **Erasure clears it** on a record it keeps, as a marked field, so such a field is `Email?` or says `erase: Erasure.retained`; a person who asked to be forgotten can't be left in a column because nobody wrote a mark. `EmailWithName` goes the same way, being an address with a name. **`data.personal_unreachable` still reads only `personal:`**: refusing a shop's own `support_email` would need a mark saying an address isn't personal, and the pages have none; the reasoning for a shop's own phone number holds. **No opt-out:** a business's address is listed, noticed and accepted like any other, each of which passes or takes one line |
| Phone numbers, names and postal addresses are cleared as an email is (Richard, 2026-11-04; chunk A21) | `PhoneNumber`, `PersonName`, `GivenName`, `FamilyName` and `PostalAddress` were personal data whatever held them already. Erasure now clears them on a record it keeps with no `personal:`, exactly as `Email`: such a field is optional or says `erase: Erasure.retained`, or it is `data.erase_field_required`. A person who asked to be forgotten is left in a column by their phone number or name as much as by their address. `GivenName` and `FamilyName` go with `PersonName` because they are names. **`data.personal_unreachable` still reads only `personal:`**, so a shop's own number isn't refused there, and there is no opt-out mark, for the reasons `Email` has. A business's number copied onto a record erasure keeps is cleared with it. **Left out:** `PostalCode`, `Username`, `PhoneExtension`, `Uprn`, `Nationality` and the financial, government and health types stay cleared only when marked; what else these types do (logs, report, cache, model, audit, acceptance) doesn't change |
| Erasure at providers | The package's `erasure: { call: by: }`, the connection's `erasure: { key: }`; the app erased first in one transaction, then each provider by a generated subscriber after commit, retried until confirmed; the completion email only when all confirm; parked deliveries shown; personal keys only in the outbox until delivered; a connection that cannot erase needs an acceptance stating why; OAuth grants deleted and revoked |
| Erasure at providers, as built (chunk V6) | `ErasureNotPossible.data_stays`, its subject the connection. It says how things stand rather than what a change did, so it is needed until an acceptance the before side holds, and the project still has, lists it with a reason: a project already sending needs one on its next judged change, and later changes need no other. It covers the connection, as the page says, and a new field sent there later shows in the review's difference of the report. Without a before side nothing is judged, as for every acceptance (Richard, 2026-10-30), and the report says no acceptance says why. It counts every row of the report, a standard type that is personal data too, because the page says "personal data": a shop's own number is a one-line acceptance, and missing a person's is data that stays unseen. **A provider's answer also counts, and its row says so** (2026-11-01): the compiler can't tell a made id from the name echoed back, since nothing models what a provider puts where and `c.name` of an answer reads like `c.id`; the page's own email used as a key means an id may be the data; and an id a provider holds for a person still identifies them at whoever receives it. A disk store is the app's own, so it needs none, and a driver connection, SMTP or a model server, has no package to declare `erasure:`, so it does. `key:` is a field of a `person: true` entity of exactly the type `by:` names, and a key on one person doesn't let off what erasing another reaches, since erasing them couldn't ask the provider |
| Erasure at providers, as built | A key on the person's record is copied by the erasure's statement into the outbox payload's `keys`, one per connection, never into the event's value, so no app subscriber can read it; a generated `erasure at <connection>` subscriber reads it, calls the package's operation with the key in the field `by:` names, spelt as its wire name, and takes the key out of the payload once the provider confirms. A person with no key there is not asked about there. **A provider's `not_found` failure counts as confirmed** (decided 2026-11-11, Richard accepting the recommendation): after a lost answer the retry finds them gone, and a person the provider never knew has nothing to erase. Other failures settle as any delivery's do: retried while retryable, up to the month, else `failed` for an operator, the key kept for the retry; an erasure call that went out with no idempotency key and lost its answer is parked `outcome_unknown` like any such call, which `jadpo deliveries retry` finishes. **An encrypted field can't be a key** (`data.encrypted_field_used`, decided 2026-11-11, Richard accepting the recommendation): only the application can open it, and the statement that copies the key runs in the database. The report lists a key that is personal data in a section of its own, whether or not that connection receives anything else |
| The rest of the report, as built | Each person entity's section lists the entities an export reads, so the fields, the categories and who may read them are what export and erasure act on. Who may read a field is its own list where it has one, else its record's, as the permissions report shows it. **Decided 2026-11-11, Richard accepting the recommendation, since the page doesn't say:** a marked field counts as read by a query, by code reading it off a record, by a whole record given back or put in an object, an event or a failure, by being sent through a connection, and by a `search:`, a `unique:`, a provider's erasure key or the field identifying a caller; a test, a fixture, a seed and an export don't count, since the page names only the app's own uses and an export reads every field. A standard type on an entity no person's records reach, a shop's own phone number, gets a section of its own: the page lists fields per person, and leaving it out would say the app holds less than it does. | Records that belong to more than one person | Erasing one person never clears another person's data. | Encrypted fields, as built (chunk P9) | `field_encryption_key:` at the top of `application { }`, reading an `EncryptionKey` setting, needed only when something is kept sealed (Richard, 2026-11-01). Kept as the type's JSON in one `bytea` under a key derived from the setting, bound to `table.column` and the record's `id` by the names they were born with, so a rename changes nothing and a moved value opens for no one (chosen in chunk P9, as the sealed format's `context:` already says). | Log hashes, as built | The key is the variable `JADPO_LOG_HASH_KEY`, a deployment setting rather than a `config` value, since it is the runtime's own and no app reads it. Requiring it would stop every app that hadn't set it from starting, so left unset each process draws one of its own: the privacy holds and only matching across processes is lost, which `runtime.started` reports (`log_hash_key`). A hash reads `hmac-sha256:` and 64 hex digits, so a reader tells it from a value. A failure field's plain JSON, field by field, stands in for its contract JSON where it has no text form, since a failure's plan holds no codec for its internal fields. |
| Access records, as built | Three events, `privacy.exported`, `privacy.erased` and `privacy.read`, each with `kept: "long"` for an operator's retention to go by, in the application's own log rather than a database. An erasure's event waits for its commit, and an export's is written when it starts. A read of a sensitive field is one event per record, so a list never makes a line past a log's limit. A person's `id` comes from the record itself or its first reference to a person, or is `null` when it has neither. A write's own returned record and an aggregate leave no event: the code wrote what the first holds, and the second reads no one record. |

A failure kept by a batch's item stays in the batch's problems. A field holds a personal value when any `reject` fills it from one: the flow walk's answer, one for all the places a failure is raised. |
