# AI: design notes

Why [AI](../21-ai.md) is the way it is: the decisions behind it, how it fits the rest of the language and what it carried to other areas. An app author reads the area page, not this one.

## Related areas

- **Area 1:** `prompts/` is one of a domain's folders; `Prompt` is a type
  base; `ai` is a reserved namespace (area 19, "Reserved namespaces").
- **Area 5:** `distance:` on a vector type and `IndexKind.hnsw`; the
  derived index rule extends to `nearest`.
- **Area 6:** `nearest` in `order:`, `Nearest<T>`, and a standard
  operation (`ai.distance`) in `where:`.
- **Area 7:** `ai.stream` reaches a client through a streaming route,
  "Streaming a model's answer" (question 6).
- **Area 10:** placeholders follow translations' syntax and checks.
- **Area 11:** `ai` is in the capability table; the built-in driver is
  `Driver.openai_compatible`; `jadpo dev` fakes it as every provider call.
- **Area 13:** `recorded(...)` and `raw(...)` in `fakes:`.
- **Area 15:** `to_models: false` and `personal_data: { allowed: }`; the
  report lists prompts.
- **Area 19:** a vector is stored in a `vector` column; `distance:` sits
  beside `dimensions:` on a vector type.

## Why the area page reads as it does

The reasons behind the area page's rules; the rules themselves are on
the page.

- **Scope.** External services decided that models are reached through
  provider packages; the standard library's "Geospatial and AI" scoping
  chose the pieces Jadpo itself does, which this area specifies: the `ai`
  interface, typed answers, budgets, privacy and fakes. `ai` is a
  capability under area 11's design C, a job Jadpo performs itself and
  covers whole.
- **One `ai` connection per app.** Two, a cheap model at one provider
  and a strong one at another, wait for an app that asks, as area 11
  left sending through two email connections. Falling back to a second
  provider waits likewise.
- **Questions behind the page's rules.** Sampling settings are left to
  the provider (question 13); a price can be overridden by a setting and
  budgets are counted in the main store (question 7); the locale is a
  placeholder rather than one prompt per locale (question 5); a chat
  must list `health` (question 9); stand-ins for a person's details wait
  (question 10); keeping content in production is opt-in (question 8);
  tool calling is left to packages (question 1); IVFFlat is left out
  (question 12); vectors over 2,000 dimensions go through `halfvec`, and
  over 4,000 behind the declinable `query.nearest_exact` (question 11).
- **`prompts.render` adds no standard type.** It gives a
  `List<ChatMessage>`, the type the standard library already has.
- **No fallback without pgvector.** A search that is silently exact on
  one database and approximate on another, or held in memory, would
  behave differently from what was tested.
- **Checked against PostgreSQL.** With `, id` in the same `ORDER BY` as
  the distance, the plan is a scan of the whole table and a sort, which
  is why the tie-break is applied outside. `ai.distance` and pgvector
  were found to agree within 1e-4, relative, on model-like vectors where
  their sums aren't exact.
- **Recorded answers and warnings.** A prompt changed since a recording
  was made would be a warning; area 1 has no warning severity, so it is
  an alert on `jadpo test`'s report.

## Questions

1. **Is tool calling part of the core?** No. Agents that call the app's
   actions need answers to which actions a model may call, under whose
   policy, with what idempotency key, and how the budget spans several
   steps. Typed `generate` covers extracting, classifying, drafting and
   routing, and code acts on the answer. Tool calling, images and agent
   frameworks are packages, which extend the core; tools in the core would
   be listed actions, each run under the caller's policy with a key per
   step.
2. **Does `generate` have a fifth failure, `too_long`?** Yes. A prompt over
   the model's context is neither a refusal nor a budget: the fix is a
   shorter prompt or a larger model. It is checked before sending from the
   package's context table, so it costs nothing.
3. **How many attempts does a malformed answer get?** 2 by default (one
   repair, with the decode problem fed back), at most 3, each counted
   against every limit. With a structured-output mode a second failure is
   rare; without one, a third rarely helps.
4. **Is a prompt's text a separate `.prompt` file with two sections?** Yes,
   rather than strings in Jadpo syntax, as translations are. Prompts are
   long prose that reviewers read and diff; `# Instructions` and
   `# Request` make the split between fixed instructions and data
   visible, and the type stays in Jadpo where the checker sees it.
5. **One prompt for every locale?** Yes. A model writes in the language it
   is told, so the locale is a placeholder; translating prompts would
   multiply what must be recorded and reviewed for no gain.
6. **How does `ai.stream` reach a client?** Server-sent events
   (`text/event-stream`): a route whose `run:` returns an `AiStream`, each
   piece an event, a final event with the outcome, and a failure after the
   first piece sent as an error event. The wire format is on area 7's
   page, "Streaming a model's answer". No WebSockets.
7. **Are budgets in tokens, money or both, and where are they counted?**
   Tokens per call, per request and per caller, which the provider reports
   exactly; and per day both tokens and an estimated cost, from the
   package's dated price table with a setting to override a price.
   Counted in the main PostgreSQL store, not Redis, so counts are shared
   and never lost; a store that can't be reached refuses the call.
8. **Are prompts and answers kept in production?** Never by default.
   Keeping them is opt-in per prompt with `keep_content:`, encrypted as
   `health` data with a required `keep:`, once area 15's encrypted fields
   are built.
9. **Must a chat app list `health` to send a conversation?** Yes.
   `ChatMessage` is `health` (area 19), so every chat must allow a
   sensitive category. A transcript can hold anything; listing it puts the
   decision in front of a reviewer once, in `app.jadpo`, and the report
   shows it.
10. **Is a placeholder pseudonymised (names swapped for stand-ins and
    restored in the answer)?** No. It is useful but the restore step is
    subtle (stand-ins the model rewrites or drops); it waits for an app
    that sends names it would rather not.
11. **How are vectors over 2,000 dimensions indexed?** pgvector indexes
    `vector` to 2,000 and `halfvec` to 4,000; OpenAI's large embedding
    model makes 3,072. They are stored at full precision, indexed through
    a half-precision expression up to 4,000, and searched exactly above
    that, behind the declinable `query.nearest_exact`. Most apps should ask
    for fewer dimensions instead, which `embedding_dimensions:` does where
    the provider allows it.
12. **HNSW only, derived from queries?** Yes. HNSW builds on an empty table
    and recalls better at the same speed; IVFFlat needs its rows first.
    `indexes:` may tune `m:` and `ef_construction:`.
13. **Are sampling settings (temperature, top-p) left out?** Yes. Newer
    models restrict them and providers differ; deterministic tests come
    from the fake, not from temperature 0. A `temperature:` option waits
    for an app that shows a need.
14. **Is the distance metric on the vector type?** Yes, `distance:` beside
    `dimensions:`, default cosine. The metric belongs to the model that
    made the vectors, so a query can't compare them the wrong way and the
    derived index always matches its queries.
15. **Is the nearest-neighbour query written `order: [F nearest v]` with
    `Nearest<T>` results?** Yes, rather than ordering by `ai.distance(...)`
    directly. It reads as what it does, marks the one order an index
    serves, and `Nearest<T>` gives the distance without a computed field in
    the result type; `ai.distance` stays for `where:` thresholds and for
    code.

## Decisions

| Topic | Decision |
|---|---|
| Default timeouts | `ai.generate`'s `timeout:` defaults to 25s, its attempts staying 2, so its 50 seconds fit a route's longest deadline, 60 seconds, which a route that asks a model writes; at 60s twice no route could make the call at all. A provider connection's defaults to 3s (area 11). `ai.embed`'s and `ai.embed_all`'s to 5s, counted once in the sum since they ask once, so a search route embedding its query fits the 10-second default |
| Budgets count every send | A call's most possible use, taken from every limit before it is sent, counts the conversation each repair sends: attempt *n* sends the prompt and each earlier answer at `max_output:` with the correction that follows it (counted at 64 tokens), so `attempts: 2` takes the prompt twice, `max_output:` and 64 more tokens for the repair, and `max_output:` twice for the answers. A repair whose conversation turns out longer takes the rest from every limit before it is sent, and one a limit can't cover ends the call `over_budget`. Each send again after the provider couldn't answer (a server's error, `429`, no connection; at most 3 sends an attempt) takes the conversation it resends from every limit before it goes and is charged what it sent; one a limit can't cover isn't sent, the call ending as its last send did. So concurrent calls never pass a limit between them |
| A model's answer carries its prompt | `ai.generate`'s answer and `ai.stream`'s text, and every field read off them, carry everything the prompt was built from, each placeholder's fields and what decided them, a record or a parameter anywhere inside: a field read off the answer, `.summary`, is checked like its sources wherever it is stored (`semantic.ai_field_unmarked`, and area 9's "What a write stores") or sent to a model again. |
| What decides a value, and what is stored | `to_models: false` and `personal_data: { allowed: }` count what a condition decides: a value made under an `if` or a `match`, kept by a `list.filter`, or made after a `return` or `reject` such a condition may have taken carries the fields they test, as area 9's "What decides a value" says, so a `match` on a diagnosis sends it. Only what a loop goes through is left out (the records and rows of a `for`'s list, `list.map`'s and `list.count`'s), but for what decided which items it has, a filter's predicate among them. A create, an update or a transition storing a marked field's value, or one it decided, in a field without the same marks (each category, from `personal:` or the field's type, and `to_models: false`) is `semantic.ai_field_unmarked`, checked with what reaches a model, a parameter where it is passed and an event's part where a subscriber passes it; each problem names the field and the category, never a value. |
