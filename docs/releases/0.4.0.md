# Jadpo 0.4.0

Released 7 November 2026.

This release works with the package registry, now live at
[jadpo.dev/packages](https://jadpo.dev/packages). A provider package is a package that connects your
app to an outside service, such as Resend for email. Publishing one now checks its types, and the
package commands work against the live registry.

## Before you upgrade

- **A provider package needs a `reviewed:` list to be published.** A package's public types are
  the ones it offers to the apps that install it. `jadpo package check` refuses a release until
  `reviewed:` in `provider.jadpo` lists each of them (`publish.type_unreviewed`). Listing a type
  there records that someone checked it against the service's documentation. Your app isn't
  affected: the packages it has installed keep working.
- **A package release with a `reviewed:` list needs Jadpo 0.4.0 to install.** Jadpo 0.3.0 can't
  read a `reviewed:` list, so an app on 0.3.0 stays on the release of the package it already has.

## New

- **`jadpo package check` suggests standard types in a provider package.** Standard types are
  Jadpo's built-in types, such as `Email` and `Instant`. A field named like an email address or a
  time, but typed as plain `Text` or a number, is flagged with the standard type to use instead
  (`package.standard_candidate`). So is free text that may hold personal data and isn't marked
  `personal:`. When the plain type is right, you can decline the finding with a reason.
- **`jadpo package publish` ends with a link to the release's page on jadpo.dev.** The command
  sends the release to be checked. On its page, you confirm it with your passkey to make it live.
  With `--json`, the link is `page`.
- **`jadpo package publish` sends the publisher's name.** A publisher lists the repositories it
  releases from, so the registry can turn a release away before checking it when it comes from a
  repository that publisher hasn't listed. When the registry turns a release away, the command
  shows the registry's reason.
- **`jadpo package verify --json` gives descriptions as their own fields**: the package's, and
  those of each public type and function, under `descriptions`.

## Fixed

- `jadpo build` builds an app whose action reads a top-level `constant`. An action is a function
  in your app that reads or changes data. The build used to fail with `toolchain.build_failed`,
  though `jadpo check` passed.
- A package type with the same name as one of your app's types no longer makes `jadpo check` say a
  stored record has changed since your last migration.
- `jadpo package check` on a tagged commit compares it with the release before it, to work out
  whether the change is a patch, minor or major release. It used to compare it with the
  repository's newest tag.
- `jadpo package check` finds the changes in a provider package that sends fixed headers. It used
  to find none, so a breaking change could pass as a patch.
- A failed package test shows where it failed in your package, not in a temporary folder.
- The registry's verifier, which checks a package's code before it can go live, refuses a
  repository address that redirects. A renamed or moved repository is never fetched from its new
  owner (`publish.repository_refused`).
- In a test, `.requests` on a fake of an outside service now reports that it isn't built yet
  (`toolchain.not_built_yet`). It used to give a wrong error.
- When jadpo.dev answers a package command with "not found", the command now reports that the
  registry isn't answering, rather than that the package doesn't exist.
